# API 版本管理策略

## 1. 版本管理策略概述

### 1.1 为什么需要版本管理

API 版本管理是保障系统稳定演进的重要机制，其核心目标包括：

- **向后兼容**：确保现有客户端不受 API 变更影响
- **平滑升级**：允许客户端按需迁移到新版本
- **快速迭代**：开发者可以自由地改进 API 而不破坏现有集成
- **明确沟通**：通过版本号清晰传达变更的性质和影响

### 1.2 版本管理方案对比

| 方案 | 优点 | 缺点 | 适用场景 |
|------|------|------|----------|
| **URL 路径版本** | 直观清晰，调试方便，缓存友好 | URL 不美观，多版本路由复杂 | 大多数 RESTful API |
| **Header 版本** | URL 保持干净，符合 REST 原则 | 调试不便，缓存需要考虑 Header | 纯 API 服务，高级客户端 |
| **Query 参数版本** | 实现简单，默认版本易用 | 语义不清晰，容易被忽略 | 简单内部系统 |
| **媒体类型版本** | 完全符合 REST 规范 | 实现复杂，学习成本高 | 严格遵循 REST 的系统 |

### 1.3 项目选择的策略

本项目采用 **URL 路径版本** 策略，格式为 `/api/v{版本号}/`。

**选择理由：**

1. **直观易用**：开发者一眼就能看出正在使用的 API 版本
2. **调试方便**：直接在浏览器或 curl 中测试不同版本
3. **缓存友好**：CDN 和 HTTP 缓存可以按 URL 自然区分版本
4. **工具支持好**：NestJS 原生支持 URI 版本控制
5. **团队熟悉度高**：大多数开发者都熟悉这种模式

**当前实现：**

- 版本前缀：`api/v`
- 默认版本：`1`
- 完整路径示例：`/api/v1/auth/login`
- 配置位置：`src/main.ts` 中的 `app.enableVersioning()`

## 2. 版本号规范

### 2.1 语义化版本

API 版本号遵循 **语义化版本（Semantic Versioning）** 原则，但只使用 MAJOR 版本号在 URL 中：

- **MAJOR（主版本）**：不兼容的 API 变更，URL 中体现（v1, v2, v3...）
- **MINOR（次版本）**：向下兼容的功能性新增，在响应头或文档中标注
- **PATCH（修订号）**：向下兼容的问题修正，内部迭代不对外暴露

### 2.2 版本递增规则

#### 递增 MAJOR 版本（v1 → v2）

当出现以下**破坏性变更**时，必须递增主版本号：

- 删除或重命名 API 端点
- 删除或重命名请求参数
- 删除或重命名响应字段
- 修改字段的数据类型（如 string → number）
- 修改必填参数（新增必填项）
- 修改认证方式
- 修改请求/响应的整体结构
- 删除枚举值或修改枚举含义

#### 递增 MINOR 版本

当出现以下**向后兼容**的变更时，递增次版本号：

- 新增 API 端点
- 新增可选的请求参数
- 新增响应字段
- 新增枚举值
- 优化性能但不改变接口契约
- 新增文档或示例

#### PATCH 版本递增

以下变更只递增修订号，不对外暴露：

- 修复 Bug（不改变接口行为）
- 代码重构
- 性能优化
- 文档更新
- 测试补充

### 2.3 破坏性变更判断标准

**什么是破坏性变更？**

> 任何导致现有客户端代码在不修改的情况下无法正常工作的变更，都是破坏性变更。

**具体判断清单：**

- [ ] 请求方法是否改变（GET → POST 等）
- [ ] 端点路径是否改变
- [ ] 是否删除了原有参数
- [ ] 是否新增了必填参数
- [ ] 参数类型是否改变
- [ ] 参数取值范围是否缩小
- [ ] 响应字段是否删除或重命名
- [ ] 响应字段类型是否改变
- [ ] 状态码含义是否改变
- [ ] 错误响应格式是否改变
- [ ] 认证方式是否改变
- [ ] 限流策略是否大幅收紧

## 3. 版本迁移指南

### 3.1 新旧版本共存策略

当发布新的 MAJOR 版本时，遵循以下共存策略：

#### 共存期

- 新版本发布后，旧版本至少保留 **6 个月** 的支持期
- 共存期间，旧版本只修复安全问题和严重 Bug，不新增功能
- 两个版本共享底层服务层，通过不同的 Controller 和 DTO 隔离

#### 版本路由

在 NestJS 中通过 `@Controller({ version: '2' })` 或 `@Version('2')` 装饰器声明版本：

```typescript
// v1 版本控制器
@Controller({ path: 'users', version: '1' })
export class UsersV1Controller { ... }

// v2 版本控制器
@Controller({ path: 'users', version: '2' })
export class UsersV2Controller { ... }
```

### 3.2 Deprecation 通知机制

当某个端点或版本即将废弃时，通过以下方式通知开发者：

#### 1. 响应头警告

在即将废弃的端点响应中添加 `Deprecation` 和 `Sunset` 头：

```
Deprecation: true
Sunset: Sat, 31 Dec 2024 23:59:59 GMT
Link: </api/v2/users>; rel="successor-version"
```

#### 2. 文档标注

在 API 文档（Swagger）中使用 `@ApiDeprecated()` 装饰器标记废弃端点：

```typescript
@ApiDeprecated()
@ApiOperation({ summary: '【已废弃】获取用户信息，请使用 v2 版本' })
@Get(':id')
findOne(@Param('id') id: string) { ... }
```

#### 3. 发布说明

每次版本发布时，在 Release Notes 中明确说明：
- 新增了哪些功能
- 废弃了哪些功能
- 废弃功能的移除时间表
- 迁移指南和示例

#### 4. 主动通知

对于重要客户或集成方，通过邮件、技术支持等渠道主动通知版本变更。

### 3.3 版本移除流程

当旧版本到达生命周期终点时，按以下流程移除：

1. **提前 3 个月**：正式发布废弃通知，提供迁移指南
2. **提前 1 个月**：再次提醒，增加响应头警告频率
3. **移除前 2 周**：进行限流降级，提醒剩余用户迁移
4. **正式移除**：移除旧版本代码，更新文档
5. **移除后**：保留历史文档和发布记录供参考

## 5. 最佳实践

### 5.1 向后兼容的变更

在不增加主版本号的前提下，如何安全地演进 API：

#### ✅ 安全的变更

- 新增可选的请求参数
- 新增响应字段
- 新增 API 端点
- 放宽参数限制（如最大长度从 50 改为 100）
- 优化性能（响应时间缩短）
- 修复 Bug（不改变正确行为）

#### ❌ 危险的变更

- 删除或重命名字段
- 修改字段类型
- 新增必填参数
- 缩小参数取值范围
- 修改状态码含义
- 修改错误响应格式

### 5.2 破坏性变更处理流程

当确实需要进行破坏性变更时，遵循以下流程：

1. **评估影响**：
   - 分析变更影响的端点和字段
   - 统计活跃客户端数量
   - 评估迁移成本和风险

2. **设计新版本**：
   - 保持旧版本不变，在新版本中修改
   - 编写详细的迁移指南
   - 提供新旧版本对比文档

3. **发布新版本**：
   - 发布新的 MAJOR 版本
   - 在文档中标注旧版本的废弃时间
   - 通过多个渠道通知用户

4. **过渡期支持**：
   - 保持旧版本运行至少 6 个月
   - 提供迁移工具和技术支持
   - 监控旧版本使用量下降情况

5. **正式移除**：
   - 确认旧版本使用率为零或可接受
   - 按计划移除旧版本
   - 归档历史代码和文档

### 5.3 文档同步更新

代码变更必须同步更新文档：

- **Swagger/OpenAPI**：接口定义、参数说明、响应示例
- **迁移指南**：版本间的迁移步骤和代码示例
- **更新日志**：每个版本的变更记录
- **API 文档**：概念说明、使用教程、最佳实践

**文档更新原则：**

1. 代码和文档在同一个 PR 中提交
2. 新增功能必须有对应的文档
3. 破坏性变更必须有迁移指南
4. 文档中应包含完整的示例代码

## 6. 相关配置

### 6.1 NestJS 版本控制配置

配置位置：`src/main.ts`

```typescript
app.enableVersioning({
  type: VersioningType.URI,
  defaultVersion: '1',
  prefix: 'api/v',
});
```

### 6.2 控制器版本声明

```typescript
// 方法级版本控制
@Controller('users')
export class UsersController {
  @Version('1')
  @Get(':id')
  findOneV1(@Param('id') id: string) { ... }

  @Version('2')
  @Get(':id')
  findOneV2(@Param('id') id: string) { ... }
}

// 控制器级版本控制
@Controller({ path: 'users', version: '2' })
export class UsersV2Controller { ... }
```
