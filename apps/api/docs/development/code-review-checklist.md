# 🔍 API 项目代码审查清单

> 本清单针对牙科诊所管理系统 API 项目（NestJS + SQLite）定制，用于 Pull Request 代码审查时逐项检查。
> 请审查者根据变更范围勾选适用项，确保代码质量、安全性和可维护性。

---

## 1. 代码审查总览

### 审查目的

- ✅ 确保代码符合项目架构和编码规范
- 🔒 保障数据安全与多租户隔离
- 💰 保证财务数据一致性
- 🐛 提前发现潜在 Bug 和性能问题
- 📖 提升代码可维护性和可读性

### 审查流程

1. **自动化检查**：CI 通过（typecheck + lint + test）
2. **功能审查**：对照需求确认功能实现
3. **逐项检查**：按本清单各分类检查
4. **反馈沟通**：提出修改意见，讨论方案
5. **合并确认**：所有问题解决后合并

### 审查标准

- **正确性优先**：功能正确，边界处理完善
- **安全红线**：安全漏洞、多租户绕过、财务错误为阻断性问题
- **可维护性**：代码清晰，易于理解和修改
- **一致性**：遵循项目现有模式和风格

## 2. 功能审查清单

### 需求实现

- [ ] 代码实现了 PR 描述的所有功能点
- [ ] 业务逻辑与产品/设计文档一致
- [ ] 没有引入未在的功能（No Surprise）
- [ ] 与现有模块的交互接口正确
- [ ] DTO 定义清晰，字段完整

### 边界情况处理

- [ ] 空值处理：`null` / `undefined` / 空字符串 处理正确
- [ ] 空数组、空对象情况已处理
- [ ] 分页边界：`page=0`、`pageSize` 过大或过小
- [ ] 日期边界：开始日期 > 结束日期、跨年/跨月
- [ ] 金额边界：0 元、负数、超大金额（使用 Money 对象）
- [ ] 字符串边界：超长字符串、特殊字符
- [ ] 枚举值边界：非法枚举值的校验、新增枚举值的兼容处理
- [ ] ID 不存在的情况：返回 404 或适当错误

### 错误处理

- [ ] 使用 `BusinessException` 抛出业务异常，带明确错误码
- [ ] 错误码在 `error-codes.ts` 中定义，不重复不冲突
- [ ] 所有可能出错的路径都有错误处理
- [ ] 数据库操作失败有适当回滚或错误处理
- [ ] 错误信息对用户友好，不暴露内部细节
- [ ] 错误日志包含足够的排查信息（traceId 等）

### 数据一致性

- [ ] 涉及多表写入的操作使用了事务（`db.transaction()`）
- [ ] 事务范围合理，不包含非数据库操作
- [ ] 财务操作（收费、退款、会员卡）在事务内执行
- [ ] 金额计算使用 `Money` 值对象，无浮点数运算
- [ ] 收支平衡校验：收费金额 = 各支付方式合计 + 会员卡抵扣 + 优惠
- [ ] 软删除正确，查询时过滤已删除数据
- [ ] 关联数据一致性（删除主记录时，关联记录处理正确）

## 3. 代码质量清单

### 命名规范

- [ ] 变量、函数、类命名清晰，见名知意
- [ ] 遵循项目命名风格：
  - 类名：`PascalCase`（如 `PatientService`）
  - 方法名：`camelCase`（如 `getPatientById`）
  - 常量：`UPPER_SNAKE_CASE`（如 `MAX_PAGE_SIZE`）
  - DTO 后缀：`xxxDto`
  - 模块后缀：`xxx.module.ts` / `xxx.service.ts` / `xxx.controller.ts`
- [ ] 布尔值使用 is / has / can 等前缀（如 `isActive`, `hasPermission`）
- [ ] 避免拼音命名，不用缩写（除广泛使用的除外）

### 函数与模块

- [ ] 函数职责单一，一个函数只做一件事
- [ ] 函数行数适中，建议 ，不超过 50 行
- [ ] 函数参数不超过 3-4 个，过多时使用对象参数
- [ ] 没有重复代码，相似逻辑抽取为公共函数或服务
- [ ] 模块划分合理，符合 NestJS 模块化架构
- [ ] 依赖注入使用构造函数注入，避免硬编码依赖

### 类型安全

- [ ] 尽量避免使用 `any` 类型
- [ ] DTO 使用 `class-validator` 装饰器进行校验
- [ ] 接口返回类型明确，不返回 `any`
- [ ] 使用 branded types 用于 ID 等重要类型
- [ ] `@ApiProperty` 等 Swagger 装饰器完整
- [ ] 没有未使用的变量和导入

### 注释与文档

- [ ] 复杂业务逻辑有清晰的注释说明
- [ ] 公共方法有 JSDoc 注释（参数、返回值、说明
- [ ] 注释说明「为什么」而不是「做什么」
- [ ] 没有注释掉的代码
- [ ] TODO / FIXME 有明确的责任人或 Issue

### 代码风格

- [ ] 代码格式符合 Prettier 配置
- [ ] 缩进统一（2 空格）
- [ ] 没有多余的空行和空格
- [ ] 导入顺序规范（外部库 → 内部模块 → 相对路径）
- [ ] 遵循项目现有的代码模式和惯例

## 4. 安全审查清单

### 输入验证

- [ ] 所有用户输入都经过验证（DTO 校验）
- [ ] 使用 `class-validator` 装饰器完整
  - `@IsString` / `@IsNumber` / `@IsOptional` 等正确使用
  - 字符串长度限制（`@MaxLength`）
  - 数字范围限制（`@Min` / `@Max`）
  - 日期格式验证（`@IsDateString` / `@IsISO8601`）
- [ ] 没有直接使用用户输入拼接 SQL 或命令
- [ ] 文件上传有类型和大小限制（如有）

### SQL 注入防护

- [ ] 所有 SQL 查询使用参数化查询（`?` 占位符）
- [ ] 没有字符串拼接 SQL 语句
- [ ] 动态条件查询使用 `sql-builder` 工具类
- [ ] 表名、列名等不能参数化的部分有白名单校验
- [ ] `sql-injection.middleware` 中间件防护生效

### XSS 防护

- [ ] 用户输入的富文本内容使用 `sanitize-html` 处理
- [ ] 返回给前端的用户内容不会导致 XSS
- [ ] `helmet` 安全头配置正确

### 敏感数据处理

- [ ] 患者身份证号、手机号等敏感数据加密存储
- [ ] 使用 `encryption.ts` 中的加密工具
- [ ] 日志中敏感数据已脱敏（使用 `mask` 工具函数）
- [ ] API 返回值中敏感字段已脱敏或不返回
- [ ] 密码使用 bcrypt 哈希存储，无明文
- [ ] 没有在代码中硬编码密码、密钥、Token
- [ ] 密钥从环境变量读取，不提交到代码库

### 权限控制

- [ ] 接口有适当的认证保护（`@UseGuards(JwtAuthGuard)`）
- [ ] 公开接口使用 `@Public()` 装饰器明确标记
- [ ] 角色权限控制正确（`@Roles()` + `RolesGuard`）
- [ ] 资源所有者校验（`ResourceOwnerGuard`）正确应用
- [ ] 敏感操作（删除、修改金额）有权限校验
- [ ] 不能越权访问其他诊所或其他用户的数据

### 多租户隔离

- [ ] **所有**数据库查询都有 `clinicId` 过滤条件
- [ ] 创建操作时 `clinicId` 从 `ClinicContext` 获取，不接受前端传入
- [ ] 更新/删除操作也应用了 `clinicId` 过滤
- [ ] 全局搜索、统计等操作也正确隔离诊所数据
- [ ] 没有通过其他方式绕过诊所隔离
- [ ] 关联查询的表也都过滤了 `clinicId`

### 加密与安全

- [ ] JWT 密钥长度足够（至少 32 位）
- [ ] Token 过期时间设置合理
- [ ] Refresh Token 轮换机制正确
- [ ] bcrypt 轮数合理（生产环境建议 12 轮）
- [ ] 敏感操作有速率限制（`@RateLimit` 装饰器）

## 5. 性能审查清单

### 查询性能

- [ ] 没有 N+1 查询问题
- [ ] 大表查询有适当的索引
- [ ] 避免了全表扫描（`EXPLAIN` 验证过，复杂查询）
- [ ] 分页查询正确，没有一次加载全部数据
- [ ] 使用 `LIMIT` / `OFFSET` 正确
- [ ] 列表查询只返回需要的字段，不 `SELECT *`

### 缓存策略

- [ ] 适当使用缓存（`CacheService`）
- [ ] 缓存 key 设计合理，包含 clinicId
- [ ] 缓存失效策略正确，数据更新时清理缓存
- [ ] 没有缓存穿透、缓存击穿问题
- [ ] 统计数据使用缓存，且有正确的失效机制

### 循环与计算

- [ ] 没有不必要的循环嵌套
- [ ] 循环内没有数据库查询（批量查询
- [ ] 批量操作有适当的分批处理
- [ ] 复杂计算考虑了性能影响
- [ ] 内存使用合理，没有内存泄漏

### 数据库优化

- [ ] 新增表和字段考虑了索引
- [ ] 索引策略符合 `index-strategy.md 规范
- [ ] SQLite 特定优化（WAL 模式、busy_timeout 等）
- [ ] 事务使用合理，不长事务
- [ ] 避免在事务内有耗时操作

## 6. 测试审查清单

### 单元测试

- [ ] 新增/修改的 Service 有对应的单元测试
- [ ] 测试覆盖了主要逻辑路径
- [ ] 使用 `MockDbService` 进行单元测试
- [ ] 测试用例描述清晰，易于理解
- [ ] 测试数据合理，有边界情况
- [ ] 测试独立，不互相依赖

### 集成测试

- [ ] 复杂业务流程有集成测试（`*.integration.spec.ts`）
- [ ] 多模块协作的场景被覆盖
- [ ] 使用内存 SQLite 进行测试

### 并发与故障测试

- [ ] 涉及并发的场景有并发测试（`*.concurrent.spec.ts`）
  - 库存扣减
  - 会员卡余额更新
  - 收费/退款
- [ ] 关键路径有故障注入测试（`*.fault.spec.ts`）
- [ ] 幂等性有测试验证

### 测试质量

- [ ] 测试有断言，不只是运行不报错
- [ ] 测试了正常路径和异常路径
- [ ] 边界情况有测试用例
- [ ] 测试命名清晰，说明测试的是什么
- [ ] 所有现有测试都能通过

### README 与索引

## 8. 架构审查清单

### 分层架构

- [ ] 符合 NestJS 分层架构（Controller → Service → Repository）
- [ ] Controller 只处理请求/响应，不包含业务逻辑
- [ ] Service 层包含业务逻辑
- [ ] 数据访问在 Repository 或 Service 中
- [ ] 没有跨层调用（如 Controller 直接操作数据库）

### 模块依赖

- [ ] 模块划分合理，高内聚低耦合
- [ ] 模块间依赖清晰，没有循环依赖
- [ ] 公共功能放在 `common/` 目录
- [ ] 复用了现有的基础设施（BaseService、工具函数等）
- [ ] 没有重复造轮子

### 新增依赖

- [ ] 新增的 npm 包是必要的
- [ ] 新增依赖的包有合理的替代方案
- [ ] 依赖版本稳定，维护活跃
- [ ] 没有安全漏洞（`npm audit` 通过）
- [ ] 已评估了引入成本

### 设计模式

- [ ] 遵循项目现有的设计模式
- [ ] 使用了适当的设计模式（状态机、工厂、策略等）
- [ ] 没有过度设计（YAGNI 原则）

## 9. Git 提交审查清单

### 提交信息

- [ ] 提交信息符合 Conventional Commits 规范
- [ ] type 正确：`feat` / `fix` / `docs` / `style` / `refactor` / `perf` / `test` / `chore`
- [ ] scope 清晰：模块名（如 `patients`, `charge`）
- [ ] 描述简洁明了，说明做了什么
- [ ] 重要提交有详细的 body 说明

### 提交粒度

- [ ] 提交粒度合适，一个提交一个逻辑单元
- [ ] 没有超大提交（一个提交改了太多不相关的内容）
- [ ] 提交历史清晰，易于回滚
- [ ] 没有 WIP / 调试提交留在历史中（已 squash）

### 提交内容

- [ ] 没有提交无关文件（日志、临时文件等）
- [ ] `.gitignore` 配置正确
- [ ] 没有提交敏感信息（密码、密钥、Token 等）
- [ ] 没有调试代码残留
  - 没有 `console.log` 调试输出
  - 没有 `debugger` 语句
  - 没有注释掉的代码块
- [ ] 没有 `TODO` / `FIXME` 未处理（除非有明确说明）

### PR 相关

- [ ] PR 标题清晰，说明变更内容
- [ ] PR 描述填写完整，包含：
  - 变更背景和目的
  - 主要变更点
  - 测试情况
  - 截图（如涉及 UI）
- [ ] PR 关联了相关 Issue
- [ ] PR 标签正确（reviewer、assignee 等）
