# 剩余两项决策提案

第 15-19 轮审计修复已收口，剩余两项需要产品/架构口径。本文档给出选项、影响与推荐默认，供直接评审后进入实施。

## 决策 1：processing-flow 手动改态是否收敛为状态机

现状：`setStep` 允许从任意状态手动改为 `PENDING / IN_PROGRESS / DONE`（双击手动改），`registerStep` 按顺序推进。

选项：

- A（推荐）：保留手动改态，但增加“当前状态条件更新 + changes 校验”。手动改是产品能力，只修并发覆盖风险；不限制任意跳转。
- B：收敛为严格状态机，只允许 `PENDING -> IN_PROGRESS -> DONE`，移除手动任意跳转；需同步改造 UI 与既有数据。
- C：维持现状（不改）。

影响：

- A：风险最低，保留现有交互，仅消除多实例覆盖。
- B：语义最清晰，但会改变用户操作习惯，需要迁移说明与 UI 改动。
- C：继续登记为设计保留，审计结论不变。

推荐：A，工作量小且不改变产品行为。

## 决策 2：dashboard / replenishment 是否启动增量聚合

现状：`stats.dashboard` 与 `replenishment.generate` 冷态全表聚合；10 万级基准全部 PASS（dashboard 69ms、患者搜索 7ms），阈值暂未超。

选项：

- A（推荐）：暂不改造，以 `benchmark:load` 为回归基线；当 dashboard 冷态超过 10s 或单库行数超过 100 万时再启动。
- B：立即实施定时快照表（每日/每小时重建聚合），dashboard 读快照；需要定义刷新周期与陈旧窗口。
- C：仅对 replenishment 分批处理（每批 500 项 + 事务），降低单次同步阻塞，不做快照。

影响：

- A：零改动，已有基线可回归。
- B：dashboard 响应最稳，但引入“数据陈旧”语义与定时任务运维。
- C：补货生成仍全量扫描，但不再单事务阻塞；改动中等。

推荐：A + 预留 C 的接口（生成函数按批参数化），等阈值触发再切换。
