# ADR-0006: 数据库选型 - SQLite

## 状态
已采纳

## 日期
2026-07-24

## 背景
口腔诊所管理系统以 Electron 桌面应用形式分发，随应用一起部署到各诊所的终端机器上。
这种部署形态对数据存储提出了特殊要求：

1. **无需独立数据库服务**：诊所通常没有专职运维人员，无法维护一个独立的数据库服务器进程（PostgreSQL/MySQL）。任何需要单独安装、配置、启动的服务都会显著增加部署成本和故障面。
2. **单机运行**：每个诊所终端只需服务本机用户，不存在多节点水平扩展的需求。
3. **数据可移植**：诊所切换设备或备份迁移时，数据应能以文件形式直接复制带走。
4. **同步访问**：桌面应用的交互响应要求高，数据库调用应避免异步开销影响主流程。

项目早期曾使用 PostgreSQL + Prisma 方案，但该方案要求每个诊所部署独立的数据库服务器，运维成本过高，难以在中小诊所推广。

## 决策
选择 **SQLite**（通过 `better-sqlite3` 驱动）作为系统的数据库。

- 数据以单文件（`dental.sqlite`）形式存储在应用的 `data` 目录下
- 使用 `better-sqlite3` 同步驱动，避免 Promise/async 开销，调用方式直观
- 通过 WAL 模式提升并发读写能力

## 替代方案

### PostgreSQL + Prisma（已废弃）
- 优点：功能强大、支持多进程并发、生态成熟
- 缺点：需要独立服务进程、安装配置复杂、不适合桌面应用分发
- 结论：运维成本过高，已被替代

### MySQL
- 优点：成熟的关系型数据库
- 缺点：同样需要独立服务进程，部署形态不匹配
- 结论：与 PostgreSQL 存在相同问题

### MongoDB
- 优点：文档型存储，Schema 灵活
- 缺点：需要独立服务进程；本项目数据关系明确（患者-就诊-收费-库存），关系型更合适
- 结论：数据模型不匹配

## 后果

### 正面
- **零配置部署**：随应用启动自动创建/连接数据库，用户无需任何数据库知识
- **单文件存储**：整个数据库就是一个 `.sqlite` 文件，备份和迁移只需复制文件
- **同步 API 性能好**：`better-sqlite3` 是同步驱动，单次查询开销在微秒级，无需 `await`
- **适合桌面应用**：与 Electron 打包分发完美契合，无需额外服务依赖
- **测试友好**：支持 `:memory:` 内存数据库，测试环境无需磁盘 I/O

### 负面
- **不支持多进程并发写入**：SQLite 同一时刻只允许一个写事务。Electron 多窗口场景下需依赖 WAL + `busy_timeout` 处理跨进程竞争
- **迁移到服务端架构需切换数据库**：若未来发展为 SaaS 多诊所云端架构，需迁移到 PostgreSQL 等服务端数据库（已有迁移计划，见 `docs/architecture/database-migration-plan.md`）
- **无内置主从复制**：高可用需借助文件级备份而非数据库级复制

## 实施
- 驱动：`better-sqlite3`（同步 API）
- 连接：`src/db/database.ts` 的 `createDbConnection()`，失败自动重试 3 次
- Pragma 配置：
  - `journal_mode = WAL`（写入更优）
  - `synchronous = NORMAL`（性能与安全的平衡）
  - `busy_timeout = 5000`（跨进程写冲突时等待 5 秒）
  - `foreign_keys = ON`（强制外键约束）
  - `cache_size` / `mmap_size` / `temp_store` 等均可通过环境变量调优
- 数据库路径：优先 `DB_PATH` 环境变量，其次 `DATA_DIR`，默认 `apps/api/data/dental.sqlite`
- 自动备份：每 6 小时执行一次 `db.backup()`，保留最近 7 份，支持异地备份（`BACKUP_REMOTE_DIR`）
- 完整性检查：启动时执行 `PRAGMA integrity_check`，异常时尝试 WAL checkpoint 修复
