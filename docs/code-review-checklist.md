# 代码评审清单

> 本清单用于代码评审时逐项检查，确保代码质量和安全性。
> 针对口腔诊所管理系统的特点：多租户、财务金额、患者隐私。

## 1. 功能正确性

- [ ] 代码实现了需求描述的所有功能
- [ ] 业务逻辑正确，符合产品/设计文档
- [ ] 没有引入新的 bug 或回归问题
- [ ] 与现有模块的交互正确
- [ ] 数据库 schema 变更合理，有对应的 migration

## 2. 边界条件处理

- [ ] 空值（null/undefined）处理正确
- [ ] 空数组、空对象情况已处理
- [ ] 分页边界：page=0、pageSize 过大或过小
- [ ] 日期边界：开始日期 > 结束日期、跨年/跨月
- [ ] 金额边界：0 元、负数、超大金额
- [ ] 字符串边界：空字符串、超长字符串、特殊字符
- [ ] 枚举值边界：非法枚举值、新增枚举值的兼容处理

## 3. 错误处理

- [ ] 所有可能出错的地方都有错误处理
- [ ] 使用 `BusinessException` 抛出业务异常，有明确的错误码
- [ ] 数据库操作失败有适当的回滚或错误处理
- [ ] 外部服务调用失败有重试或降级机制
- [ ] 错误信息清晰，便于排查问题
- [ ] 前端有友好的错误提示，不会暴露敏感信息

## 4. 安全

### SQL 注入

- [ ] 所有 SQL 查询都使用参数化查询（`?` 占位符）
- [ ] 没有使用字符串拼接 SQL 语句
- [ ] 动态条件查询使用 `sql-builder` 工具类
- [ ] 表名、列名等不能参数化的部分有白名单校验

### XSS

- [ ] 用户输入数据在存储或展示前已 sanitize
- [ ] 富文本内容使用 `sanitize-html` 处理
- [ ] 前端使用 React（默认转义），没有使用 `dangerouslySetInnerHTML`（除非必要且已处理）

### 认证与授权

- [ ] 接口有适当的认证保护（JWT Guard）
- [ ] 有角色权限控制（Roles Guard）
- [ ] 不能越权访问其他诊所或其他用户的数据
- [ ] 敏感操作（删除、修改金额）有权限校验

### 敏感数据

- [ ] 患者身份证号、手机号等敏感数据在数据库中加密存储
- [ ] 日志中敏感数据已脱敏（使用 `mask` 工具函数）
- [ ] API 返回值中敏感字段已脱敏
- [ ] 密码使用哈希存储，没有明文存储
- [ ] 没有在代码中硬编码密码、密钥、Token

### 多租户隔离

- [ ] **所有**数据库查询都有 `clinicId` 过滤条件
- [ ] 创建操作时正确设置了 `clinicId`（从上下文获取，不接受前端传入）
- [ ] 更新/删除操作也应用了 `clinicId` 过滤，防止越权
- [ ] 全局搜索、统计等操作也正确隔离了诊所数据
- [ ] 没有通过其他方式绕过诊所隔离（如直接访问 ID）

## 5. 性能

### 查询性能

- [ ] 没有 N+1 查询问题
- [ ] 大表查询有适当的索引
- [ ] 避免了全表扫描
- [ ] 分页查询正确，没有一次加载全部数据
- [ ] 复杂查询有适当的优化

### 前端性能

- [ ] 列表渲染有 `key` 属性
- [ ] 避免不必要的重渲染（memo/useMemo/useCallback）
- [ ] 大列表使用虚拟滚动
- [ ] 图片资源有优化（懒加载、适当尺寸）

### 其他

- [ ] 没有内存泄漏（定时器、事件监听器已清理）
- [ ] 批量操作有适当的分批处理，避免一次性处理过多数据

## 6. 并发与事务

### 事务

- [ ] 财务相关操作（收费、退款、会员卡充值/消费）都在事务内执行
- [ ] 涉及多张表写入的操作使用了事务
- [ ] 事务范围合理，不要过大也不要过小
- [ ] 事务隔离级别适当

### 并发

- [ ] 并发场景下没有竞态条件（如库存扣减、余额更新）
- [ ] 使用了适当的并发控制（乐观锁、悲观锁、数据库约束）
- [ ] 幂等性设计：重复请求不会产生副作用
- [ ] 没有死锁风险

## 7. 数据一致性

### 金额计算

- [ ] 所有金额计算使用 `Money` 值对象
- [ ] 没有使用浮点数进行金额计算
- [ ] 金额四舍五入规则正确，符合财务规范
- [ ] 收支平衡：收费 = 支付方式合计 + 会员卡抵扣 + 优惠 等

### 数据完整性

- [ ] 数据库有适当的约束（主键、外键、唯一索引）
- [ ] 软删除正确实现，查询时过滤了已删除数据
- [ ] 关联数据的一致性（如删除主记录时，关联记录的处理）
- [ ] 统计数据与明细数据一致

## 8. 可维护性

- [ ] 命名清晰，符合项目命名规范
- [ ] 函数/方法职责单一，不要过长（建议 < 50 行）
- [ ] 没有重复代码，逻辑复用合理
- [ ] 复杂逻辑有适当的注释说明
- [ ] 有适当的 TypeScript 类型定义，避免 `any`
- [ ] 代码结构清晰，模块划分合理
- [ ] 遵循项目现有的代码风格和模式

## 9. 测试

- [ ] 有对应的单元测试，覆盖主要逻辑
- [ ] 有 E2E 测试，覆盖核心业务流程
- [ ] 测试覆盖了正常路径和异常路径
- [ ] 测试用例描述清晰，易于理解
- [ ] 测试数据合理，有边界情况
- [ ] 所有现有测试都能通过

## 10. 文档

- [ ] 公共 API/方法有 JSDoc 注释
- [ ] 复杂业务逻辑有说明文档
- [ ] 数据库 schema 变更有 migration 说明
- [ ] 接口文档已更新（如果有）
- [ ] README 或相关文档已更新（如需要）

---

## 评审结论

- [ ] ✅ 通过，可以合并
- [ ] ⚠️ 有小问题，修改后可以合并
- [ ] ❌ 有严重问题，需要重新评审
