# 深度审计报告-第四十轮-主报告

日期：2026-08-12

基线：`4c22569` / `3c0cf0d`（上一批 keyset 分页与聚合快照优化）。本轮聚焦复核这两批优化的真实生效路径，并全量复查 electron、基础设施、分页、限流、TtlCache、备份恢复与快照失效边界。

## 1. 结论

本轮发现并修复 4 个真实问题，其中 2 个属于“功能实际上从未生效”级别：

- keyset 游标首屏/复合游标缺陷：原实现只有携带 `cursor` 的请求才返回 `nextCursor`，导致 `fetchAllPages` 与前端游标分页首屏拿不到游标，游标路径实际从未被激活；同时默认 `createdAt DESC` 列表按 `id ASC` 游标续页会吞数据/顺序错乱。已改为首屏即返回 `nextCursor`、`createdAt|id` 复合游标按 `createdAt DESC + id DESC` 续页、`id` 裸游标仍按 `id ASC`，并用 `pageSize+1` 探测末页，避免最后一页多一次空请求。
- ReplenishmentSnapshot 从未复用：窗口 `since/now` 每次调用都含毫秒，第二次生成必然窗口不匹配而全表重算；且 `MAX(createdAt)` 未按诊所过滤，跨诊所写入会误失效本诊所快照。已按 UTC 日对齐窗口并补 `tenantAnd(clinicId)`。
- Patient 默认列表（`clinicId + createdAt DESC`）缺少支撑索引，患者页 keyset 路径在大库下仍可能全表排序。已新增 `idx_v2_perf_patient_clinic_created`。
- dashboard 快照时间戳由 `new Date()` 改为 `context.now()`，与请求上下文时钟一致。

门禁：单测 225 文件 / 2268 用例、typecheck、lint、knip、build、electron:compile、benchmark:load（10 万级全部 PASS）、smoke:delivery（API/UI/load/state-machine concurrency 全部 PASS，`ALL_DELIVERY_SMOKES_PASSED`）、security:scan（692 文件）全部通过。verify:package 在本机无签名证书的构建下需按脚本既有约定设置 `V2_SKIP_PUBLISHER_NAME_CHECK=1` 与 `V2_SKIP_INTERNAL_CERT_CHECK=1` 后通过；正式签名发布由 CI 注入证书后严格校验。

## 2. 本轮问题明细

### 2.1 keyset 游标（P1，已修）

- `repository.findMany` 只在带 `cursor` 时生成 `nextCursor`，首屏无游标，前端 `fetchAllPages`/`useCrudResource` 的游标路径全部落到 offset 分页。
- 默认 `createdAt DESC` 下，旧逻辑把任意 cursor 当 `id > cursor`，与列表排序不一致，可能跳行/重复。
- 游标格式未区分：裸 id 游标被误当成复合游标解析（测试实际暴露为返回 4/3 而非 2/3）。
- 末页判定用 `rows.length === pageSize`，最后一页恰好满页时会多返回一个游标并触发一次空请求。

修复落点：`apps/v2/src/server/infrastructure/repository.ts`；新增复合游标测试、`fetchAllPages` 游标路径测试。

### 2.2 补货快照（P1，已修）

- 窗口未对齐导致物化快照每次生成都重算，大库（InventoryTransaction > 10 万）下该优化形同虚设。
- `MAX(createdAt)` 未按诊所过滤，多诊所部署下 A 诊所新增流水会持续打掉 B 诊所快照。

修复落点：`apps/v2/src/server/application/service-modules/replenishment.ts`；新增 `replenishment.spec.ts` 覆盖同日复用、跨诊所不误失效、跨天重算。

### 2.3 患者分页索引（P2，已修）

`Patient` 没有 `(clinicId, createdAt)` 索引，默认 `createdAt DESC` keyset 查询在大库下仍要排序。新增索引并在 `database.spec.ts` 断言。

## 3. 问题回答

### 我觉得我遗漏了什么

诚实结论：没有逐字读完全部代码。本轮是对最近两批改动、高风险模块（electron、repository、rate-limit、TtlCache、快照、备份）的精读加全仓模式扫描；历史遗留大模块依赖前 39 轮审计与既有测试基线。尚未覆盖的边界包括：打包后实机安装/升级演练、真实微信网关、CA 证书链路、legacy schema 完全等价性。

### 你觉得我遗漏了什么

- 建议把每轮门禁固化为一个一键脚本，并把“keyset 首屏是否生效”“快照是否真的复用”这类行为纳入 benchmark/load 回归，避免后续优化再次“写了但没生效”。
- `benchmark:load` 目前只覆盖 dashboard/搜索/同步，可补 patients 游标翻页与 replenishment 连续生成场景。
- 目录命名：`src/web/appointments|inventory`（共享辅助）与 `src/web/pages/appointments|inventory`（页面）同名易混淆；内容不重复，但建议后续收敛命名。

### 我最害怕什么

- 并发资金/库存一致性：扣款、退款、库存增减的原子性与 lost-update 防线一旦有遗漏路径，线上会直接产生金额或库存错账。
- 跨诊所边界：任何一条查询/更新漏掉 `clinicId` 都会造成数据越权可见或串诊所，本轮正是在快照校验里找到一条跨诊所泄漏（虽只是性能误失效，不是数据泄露）。
- SQLite 异常退出完整性：WAL、事务边界、主进程被杀后的孤儿 API 进程已有多层防护，但物理机断电/磁盘满这类场景仍无法在纯单测中完全证明。

### 技术风险、隐藏 bug、边界、性能、安全、重复、维护、扩展、异常、日志、目录、死代码

- 技术风险：最大的是“优化路径未生效但表面通过”（本轮已抓到两处）；其次是快照类缓存依赖写路径全部走 `trackResourceWrite`，一旦新增直写 SQL 漏调，dashboard/补货会静默变旧。
- 隐藏 bug：本轮已修 4 个；剩余风险集中在回填/历史流水（`MAX(createdAt)` 对“事后插入的旧时间流水”不失效）、实时增删下的分页漂移。
- 边界：非 `createdAt DESC`/`id ASC` 排序不返回游标（offset 兜底，语义安全但不快）；`createdAt IS NULL` 的复合游标理论上有续页断档，实际插入路径恒非空。
- 性能：`COUNT(*)` 每页仍全量统计，游标只消除深 offset 扫描；大搜索词 + FTS 尚可，LIKE 搜索字段多时会放大开销；已补 Patient 索引降低最大风险。
- 安全：本轮复查未新增风险；IPC 白名单、CSP、租户过滤、JWT/密钥落盘（0o600 + safeStorage）、登录退避、refresh token 重放撤销均有测试。残余风险是自定义 SQL 直写路径必须持续走 `trackResourceWrite`。
- 重复代码/文件/目录：698 个源文件 SHA-256 无重复；仅 `web/appointments|inventory` 与 `pages/` 同名目录易混淆；`src/shared` 与 `src/server/shared` 命名撞车。
- 维护性：repository 的 keyset 分支已收敛为单一实现；剩余建议是给 `parseFilters`/搜索条件做统一 AST，避免未来新增运算符时多处复制。
- 扩展坑：在通用 `/resources` 上叠加“按列直查”或“跨表 JOIN 分页”时，keyset 需要新增复合游标编码；快照失效集合需要随 dashboard 指标表同步扩展。
- 异常处理：本轮未发现新的静默吞错；`crashLog`/`notify`/错误窗与 API 重启链路完整；backup 的 marker 清旧-验证-签名-apply 顺序正确。
- 日志/错误提示：请求日志、health 上下文、备份清理告警均有；剩余是小概率路径（日志轮转失败）静默丢弃，属 best-effort 范畴。
- 文件过多：web 侧按功能域 + pages 分目录，总量 300 左右源文件，属于可控；若继续增长，可按路由懒加载 + `pages/<域>/<页>` 收敛，并把同名共享辅助目录改名为 `features/<域>/shared`。
- 无用代码/死代码：knip 通过，无未引用导出/文件；仅 `api-process.cjs` 中 legacy 导入相关的 TODO（迁移完成后移除）与既有文档记录的占位。
