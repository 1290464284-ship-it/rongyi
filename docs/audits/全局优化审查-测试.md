# 全局优化审查 — 测试与质量门禁

> 只读审计。证据来源：`docs/audits/flaky-ledger.md`、`apps/v2/scripts/flaky-*.mjs`、`apps/v2/scripts/quality-score.mjs`、`apps/v2/scripts/v8-ignore-report.mjs`、`apps/v2/stryker.conf.mjs`、`apps/v2/vite.config.ts`、`apps/v2/vite.web-coverage.config.ts`、`.github/workflows/v2-ci.yml`、`apps/v2/reports/mutation/mutation.json`、`apps/v2/quality/*.json`、`docs/architecture/coverage-exclusions.md`，以及一次 `vitest run --reporter=verbose` 全量回归（298 文件 / 3267 用例，83.05s 墙钟，test 688.89s → 约 8.3x 并行）。

---

## 1. 高优先级（门禁真实性问题）

1. **通用 CRUD 路由的权限强制分支被 `v8 ignore next` 排除，而该分支真实可测且已被测试。**
   `apps/v2/src/server/http/router.ts:50-55` 的 `requiredPermission && !permissions.includes(...)` 403 分支被 `v8 ignore next`（50/52/54 行）整体排除。这是授权核心路径，不是死代码：`router.spec.ts:252-256`、`527-532` 已在测 FORBIDDEN/403。影响：覆盖率口径在最高价值的授权代码上失真——分支既可达又被测，却因标记不计入，等于门禁对授权回归“闭眼”。建议：删除该三处标记，让 spec 直接计入覆盖率；确要保留则必须在 `coverage-exclusions.md` 登记（当前该文件对 router.ts 无任何条目）。

2. **repository.ts 多达 33 处 `v8 ignore`，多落在真实可达分支，且均未在 `coverage-exclusions.md` 登记。**
   典型：`apps/v2/src/server/infrastructure/repository.ts:175-178`（过滤器标量校验，传数组/对象即抛 ValidationError，真实可达）、`:390-391`（软删表 `deletedAt IS NULL`）、`:417-419`（`changes===0` → NotFound）、`:455-456`/`:465-466`（softDelete 零变更 NotFound）、`:301-309`（keyset 游标 createdAt/通用/id 三种编码分支）、`:481-485`（患者子表索引清理）。影响：这些是数据访问正确性与防越权的关键守卫，被批量标为“不可达”，覆盖率 100% 因此显著虚高。建议：去掉 marker 并为这些分支补端到端用例（多数已可用真实 SQLite 触发）。

3. **v8-ignore 基线在“清理”后重新膨胀：145 → 294 处，与登记册自相矛盾。**
   `docs/architecture/coverage-exclusions.md:24-27` 声称 2026-08-13 清理后“145 处（15 文件）”，实测服务端 branches 90.92%；`apps/v2/quality/v8-ignore-baseline.json:3` 现为 **294 处**，且 `coverage/coverage-final.json` 实测服务端 branches **100%**。同文件 `:5-6` 又仍写“基线 525 处”。影响：登记册与实际基线脱节约 149 处新标记，绕过了“新增排除必须先登记”的自身规则（`coverage-exclusions.md:6`）。建议：重新核算并逐条登记 router.ts/repository.ts/sync.ts/user-management.service.ts 的裸标记，否则视为违规新增。

4. **变异得分 100% 由“窄范围 + 全量等价白名单”构造，而非全库真实性。**
   `apps/v2/stryker.conf.mjs:4-24` 只突变 14 个文件/区间；`reports/mutation/mutation.json` 实际 2217 个变异中 **1298（58.5%）状态为 Ignored**（静态，从未跑测试），902 Killed + 4 Timeout + 13 Survived。`quality-score.json:23-30` 只把 906+13 计入分母得出 1.0。影响：“mutation 100%”掩盖了半数变异未被执行、且突变面远小于服务端代码的事实。建议：把 Ignored 数量显式纳入质量分输出并扩大 mutate 范围；至少让评分公式或报告暴露“ignored/total”。

5. **提交的质量分产物不可复现：等价白名单与 mutation.json 已失配。**
   `apps/v2/quality/equivalent-mutants.json:90-94` 登记 `wechat-reminder.ts:270`，而 `reports/mutation/mutation.json` 幸存变异在 `wechat-reminder.ts:281`（源码已挪行）。实测对账：12 匹配、1 失配、1 条 stale。影响：当前提交态下重跑 `test:quality-score` 会因 stale 白名单 `process.exit(1)` 拒绝出分（`quality-score.mjs:103-105`），`quality-score.json` 的“100”是冻结快照。CI 因 mutation 先于 quality-score 运行而自愈（`v2-ci.yml:87-100`），但本地 `verify` 顺序同样先 mutation，问题在于提交的 artifacts 彼此不自洽。建议：同步更新白名单行号（或改为内容匹配），并让 quality-score 强制引用同一轮产物。

6. **覆盖率阈值远低于实测，失去回归拦截力；真实护栏只剩“100 基线”一条。**
   `apps/v2/vite.config.ts:56-61` 服务端阈值 statements 95 / branches 85 / functions 97 / lines 95，而实测 **100%**；`vite.web-coverage.config.ts:16-21` Web 阈值 branches 75，实测 **99.91%**。影响：branch 掉 10~15 个百分点仍通过 vitest 门禁，唯一能拦住的是 quality-score 的 100 基线（`quality-baseline.json:3`），但该基线本身依赖上文的 v8-ignore 与白名单。建议：把阈值上调到“实测 −2%”，并保留 ratchet。

7. **quality-score.json 的 web 覆盖率与最新 coverage-web 产物不一致（快照陈旧）。**
   `apps/v2/quality-score.json:11-16` 记录 web 四项 = 1.0，但 `coverage-web/coverage-final.json`（18:13 重新生成）实测 lines 99.87 / branches 99.91。`quality-score.json` 生成于 16:19。影响：评分产物落后于真实产物，容易掩盖最后一次改动引入的未覆盖行。建议：评分脚本读取的 coverage 文件与写入的 score 保持同轮。

## 2. 中优先级（测试质量）

1. **时间敏感用例用真实墙钟 sleep，而非 fake timers——flaky 的盲区。**
   `apps/v2/src/server/application/service-modules/auth.service.spec.ts:87` `setTimeout(resolve, 5100)`（5.1s 真实等待）；`src/server/infrastructure/logger.spec.ts:156` 700ms；`src/web/hooks/use-crud-resource.spec.tsx:432/505/593/674` 各 400ms；`src/web/pages/system/SystemOperationsPage.spec.tsx:48/127/133/170/224` 各 350ms；`src/server/infrastructure/database.spec.ts:46` 退避 sleep。影响：shuffle 探测只抓顺序依赖，抓不到墙钟抖动；这些用例在慢 CI runner 上易超时/偶发失败，且无谓拖慢套件（auth 单用例 5.1s）。建议：改用 `vi.useFakeTimers()` + `advanceTimersByTimeAsync`，与 rate-limit/ttl-cache/scheduler 的既有正确做法对齐。

2. **“v8 采集缺陷”类 ignore 用排除掩盖覆盖合并缺陷，而非修复采集。**
   `apps/v2/src/server/http/routes/workflow.ts:40,93,122,125,139,214,240,271,364,383` 及 `pay-method.ts:41`、`clinical-workflow.repository.ts:46-48` 等，以“spec 已真实执行、全量合并时 v8 不入账”为由整段排除。影响：这些分支其实可达且被测，却被排除——覆盖率数字与真实行为再添一层失真，且“合并丢失集合随运行浮动”（`coverage-exclusions.md:117`）本身就是不可靠信号。建议：优先修 v8 合并（如改用 `--coverage.ignoreEmptyLines`/统一单进程收集或移除 `v8 ignore` 后接受真实百分比），再谈排除。

3. **backup 故障注入依赖手写 mock DB 对象，断言偏实现而非行为。**
   `apps/v2/src/server/application/service-modules/backup.spec.ts:65-110` 用 `{ backup: async()=>{...}, pragma: vi.fn(), prepare: vi.fn(()=>({run:...})) }` 模拟 better-sqlite3。影响：这类 mock 结构一改（如新增 `pragma`/`transaction` 调用）测试仍绿，属脆弱假绿风险；好在同文件 `:24-47` 的 staged 清理用真实 fs+SQLite，质量尚可。建议：故障路径优先用真实 DB + 真实文件锁/只读目录触发，mock 仅限无法构造的极端。

4. **大量 `setTimeout(resolve, 0)` / `setImmediate` 微观 flush 依赖事件循环时序。**
   遍布 `ChargesPage.spec.tsx:607`、`TreatmentsPage.spec.tsx:164`、`VisitsPage.spec.tsx:173`、`DispenseWorkbenchPage.spec.tsx:271/350` 等。影响：单测内通常稳定，但属于隐性时序耦合，与 fake-timer 混用时易踩坑。建议：统一用 `act(async()=>{})`/`waitFor` 替代裸 `setTimeout 0`。

5. **状态机路径的“真实行为”覆盖好，但部分分支靠“探针验证执行 + v8-ignore”两段式自证。**
   `VisitsPage.tsx:121`、`TreatmentsPage.tsx:131`、`ProcessingOrdersPage.tsx`（多处）、`PatientTimelinePage.tsx:73/119` 均采用“spec 已覆盖 + 探针验证执行 + v8 不入账即排除”模式（见 `coverage-exclusions.md:78/92`）。影响：行为确实被验证（探针真实断言 PATCH 次数），但覆盖率口径不承认它，长期造成“测试很全、覆盖却靠标记”的错觉。建议：把探针断言固化为公开可读的测试断言，并逐步移除对应 ignore。

## 3. 低优先级（打磨）

1. **flaky 检测窗口过窄：只看最近 3 次运行。**
   `apps/v2/scripts/flaky-report.mjs:10-13` 与 `quality-score.mjs:23-27` 均 `history.slice(-3)`；`flaky-quarantine/history.json` 显示 08-14 曾连续 4 次 `passed:false`，随后全绿，故当前 `flakinessRate=0`。影响：偶发抖动（本就间歇）极易滑出窗口，反 flaky 分数失真为恒 100%。建议：改为时间窗（如最近 14 天全部记录）或最近 N≥10 次。

2. **CI 门禁内 shuffle 只跑 1 轮。**
   `.github/workflows/v2-ci.yml:82-85` `FLAKY_RUNS: 1`；`flaky-detect.mjs:7` 默认 2，夜扫 `v2-flaky.yml:39` 为 2。影响：PR 门禁对顺序泄漏的检出力减半。建议：PR 门禁至少 2 轮，或抽检子集多次。

3. **`coverage-exclusions.md` 多处陈旧：基线数、标记数、变异阈值均未同步。**
   `docs/architecture/coverage-exclusions.md:5-6`（525 基线）、`:24-27`（145 处 / 90.92%）、`:41`（mutation high 82/low 77/break 75）分别与现实 294 处、100% branches、`stryker.conf.mjs:59` 的 high 96/low 93/break 90 不符。影响：登记册失去“唯一登记处”的权威，后来者无法判断哪些是登记过的排除。建议：每次更新基线时同步本文件数值。

4. **`v8-ignore-report.mjs` 只约束总数，不约束每文件。**
   `apps/v2/scripts/v8-ignore-report.mjs:50-57` 仅比较 `total`，`perFile` 记录但不校验。影响：可在 A 文件删、B 文件加等量标记仍通过 ratchet，掩盖把关键文件（router/repository）新排除的行为。建议：对 perFile 也做 ratchet，或按文件类（server 核心/页面）分别设上限。

5. **`quality-score.mjs` 公式未使用 server statements/functions，且 coverage 与 mutation 权重可被单一维度“拉满”覆盖。**
   `apps/v2/scripts/quality-score.mjs:126-135` 只用 `serverCoverage.branches/lines` 与 `webCoverage.branches`，20% 变异 + 25% 路由 + 10% flaky。影响：函数/语句覆盖退步不影响分数，且 100 分依赖四项全部人为拉满（100% 覆盖、100% 变异、100% 路由、0 flaky），抗扰动差。建议：纳入 statements/functions 并给各维度加“实测基线 ±容忍”而非硬 100。

6. **测试性能整体良好，少数重 spec 可优化。**
   全量 83.05s / 3267 用例，多数用例 <50ms；相对慢者：`auth.service.spec.ts`（5.1s sleep）、`SystemOperationsPage.spec.tsx`（350ms×多处）、`use-crud-resource.spec.tsx`（400ms×4）、`MemberCardQuoteDialog.spec.tsx`（212ms）、`PrescriptionForm.spec.tsx`（271ms）。`vite.config.ts:47` 统一 `testTimeout: 20_000` 较宽松。建议：清理真实 sleep 后可将超时收紧到 10s，暴露真正挂起；变异 `stryker.conf.mjs:54` `concurrency:1`（约 13 分钟）是 CI verify 最大单项，可评估分片并行。

## 4. 正面结论

1. **规模与稳定性扎实**：298 文件 / 3267 用例全绿；`test:flaky` 完整 `--sequence.shuffle`（含文件内顺序）近 5 轮连续通过，flaky-ledger 记录的真实顺序泄漏均已修复（`docs/audits/flaky-ledger.md:34-57`）。
2. **时间敏感测试的主流做法正确**：rate-limit、ttl-cache、scheduler、audit-buffer、disk-monitor、stats-service、dialog/toast、wechat-reminder TTL 均使用 `vi.useFakeTimers`（grep 156 处命中），只有少数反例（见中优先级）。
3. **端到端深度强于多数同类项目**：备份/权限/状态机相关 spec 用真实 SQLite + 迁移（`permissions.spec.ts:28-56`、`backup.spec.ts:24-47`），且 CI 有 `smoke:permissions`、`disaster:drill`、`drill:crash`、`verify:database`、`verify:foreign-keys`（`v2-ci.yml:208-244`）做单测之外的链路验证。
4. **防自欺机制真实存在**：`quality-score.mjs:88-110` 对缺失/空输入/stale 白名单一律拒绝出分，`quality-metrics.mjs:8-10` 明确空输入不得折算 100%；这些是质量分体系里最值得保留的部分。
5. **测试并行度良好**：test 累计 688.89s / 墙钟 83.05s ≈ 8.3x 并行，CI verify/smoke 拆分为两个 job 并独立限时（`v2-ci.yml:44-48,143-144`），失败可局部重跑。

## 5. Top 5 建议

1. **清除安全关键路径上的假排除**：删除 `router.ts:50-55`（权限 403）、`repository.ts:175-178`（过滤器校验）的 `v8 ignore next`，用现有/新增真实用例计入覆盖率；无法删的必须在 `coverage-exclusions.md` 逐条登记（现状这两文件 59 处标记零登记）。
2. **修复等价白名单失配并让质量分可复现**：把 `equivalent-mutants.json` 的 wechat-reminder 行号（270→281）对齐，或改按“文件+变异算子+替换内容”匹配忽略行号；每次出分强制与同轮 mutation/coverage 产物绑定。
3. **把覆盖率阈值上修到实测−2%，并升级 v8-ignore ratchet 到每文件粒度**：`vite.config.ts` branches 85→98（server）、`vite.web-coverage.config.ts` branches 75→98，杜绝“掉 15 点仍绿”；`v8-ignore-report.mjs` 对 perFile 同样 ratchet。
4. **消灭真实墙钟 sleep，改为 fake timers**：优先 `auth.service.spec.ts:87`（5.1s）、`logger.spec.ts:156`（700ms）、`use-crud-resource.spec.tsx`（400ms×4）、`SystemOperationsPage.spec.tsx`（350ms×N），既提速也消 flaky 盲区。
5. **收紧 flaky 与变异指标的真实性**：`flaky-report.mjs` 由最近 3 次改为 14 天时间窗、CI `FLAKY_RUNS` 由 1 提为 ≥2；`quality-score.mjs` 把 mutation 的 Ignored 数量计入输出并把 mutate 范围从 14 文件继续外扩。
