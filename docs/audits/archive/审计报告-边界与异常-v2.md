# 口腔诊所系统 v2 审计报告（apps/v2）

审计范围：Electron + React + Express 5 + better-sqlite3 桌面应用（约 20k 行 TS）。
审计维度：静默吞错 / Express 错误处理 / 业务边界条件 / 用户提示 / 日志质量 / 生命周期。
全部条目均为逐文件阅读代码并部分运行验证（better-sqlite3 NaN 绑定、FTS5 空查询、`JSON.stringify(Error)` 等行为已实测）后确认，未验证的推断一律不列。

---

## 一、严重（Critical）

### C1. 迁移 116 在含历史数据的库上必然失败 → 每次启动崩溃循环
- 文件：`src/server/infrastructure/migrations.ts:497-636`（`ensureForeignKeys` 实现于 691-724，入口 `main.ts:58`）
- 场景：已有 v1 数据的诊所升级后启动。迁移 116 对 MemberCard / Refund / ChargeItem / PurchaseOrderItem / InventoryTransaction / ProcessingOrder 重建表，重建时执行 `INSERT INTO 新表 SELECT ... FROM 旧表`（717-720 行），新表带新约束：`CHECK (balance >= 0)`、`CHECK (amount > 0)`、`CHECK (quantity >= 1)`、`CHECK (price >= 0)`、`UNIQUE(clinicId, cardNo)`、`FOREIGN KEY ... REFERENCES Patient(id)` 等。只要旧数据存在任意一条负数余额、0 金额退款、0 数量明细、重复卡号、孤儿外键，INSERT SELECT 即抛错。
- 后果：迁移事务回滚（739-743 行），`runMigrations` 抛异常 → 服务进程启动即退出 → Electron 无限重启（见 L2），应用永久打不开，且没有自助修复路径，错误只在日志里。
- 建议：迁移前先对旧数据做规范化修复（负数余额钳为 0 并写修复记录、重复 cardNo 去重/加后缀、孤儿 FK 置 NULL 或告警）；迁移失败时写明确的错误标记文件并在 UI 展示具体修复指引，而不是静默无限重试；升级前自动备份。

### C2. 恢复备份 marker 校验失败 → 启动崩溃循环，且不删 marker
- 文件：`src/server/infrastructure/restore-apply.ts:31-33`，调用点 `src/server/main.ts:55`
- 场景：stageRestore 写入 `.restore-pending.json`（backup.ts:135-136）。重启时若 stagedPath 非法、越出允许目录、或文件已丢失（用户清理目录、磁盘故障），applyStagedRestore 抛错且**不删除 marker**（对比：JSON 损坏时 23-26 行会安全丢弃）。
- 后果：每次启动都失败 → Electron 无限重启（同 C1 机制），用户无法通过"再恢复一次"自愈；必须先手动删除 marker 文件。
- 建议：校验失败时把 marker 改名保留（如 `.restore-pending.invalid.json`）供排查并**继续正常启动**；或在 UI 提供"跳过本次恢复"按钮；失败时在桌面端明确提示"恢复文件无效"而不是"检查端口占用"。

### C3. DebtService.pay 非原子：欠费已收、收费单未更新
- 文件：`src/server/application/service-modules/financial.ts:686-719`
- 场景：还款先 `updatePaid` 更新 Debt（699 行），再单独 `UPDATE Charge`（711-715 行），两步之间无事务。第二步失败（磁盘满、SQLITE_BUSY 超过 busy_timeout、触发器/外键错误）时欠费已收但收费单未平。
- 后果：真实资金账目不一致；且 withIdempotency 失败后删除幂等记录（idempotency.ts:66-67），重试时 remaining 已变小 → 报"Invalid debt payment amount"，钱收了账平不了，无法自愈。
- 建议：整个 pay 包进 `db.transaction`；或先写 Charge 再写 Debt，并让失败可幂等重算。

## 二、高（High）

### H1. Electron 重启计数永远到不了上限：无限退避重启 + 首次启动失败时窗口不出现
- 文件：`electron/main.cjs:184-205`（exit 处理）、`187-188`（60s 窗口重置）、`575`（`await startApi()` 失败后不创建窗口）、`120-147`（waitForApi 15s）
- 场景：API 进程崩溃后，`now - apiLastCrashAt > 60_000` 时计数归零。按退避序列 30s→60s→120s→300s 推演：第 4 次崩溃距第 3 次已 120s > 60s，计数被重置为 0，"crashed" 分支（192-196 行）**永远不可达**（已逐行验证计数序列 1,2,3,4→1,2,3,4…）。若首次启动即失败（迁移/恢复/端口错误导致 waitForApi 15s 超时），`whenReady` 的 `await startApi()` reject → `createWindow()` 不执行 → **主窗口根本不出现**，只剩托盘图标，用户以为软件坏了。
- 后果：持续崩溃时用户只看到"重启中"或什么都没有；恢复时间最长 5 分钟间隔且无限循环；错误提示（"检查端口占用"）对迁移失败、恢复失败等场景完全误导。
- 建议：改用"启动后固定次数内失败即停"的计数（不按间隔重置）；`whenReady` 中 startApi 失败也要创建窗口并展示错误页；把 C1/C2 的失败原因映射到具体的中文修复指引。

### H2. 同步 pull 无正确游标：变更超过 1000 条即永久丢失
- 文件：`src/server/application/service-modules/sync.ts:41-48`
- 场景：`pull` 按 `createdAt > since` 取前 1000 条，返回的 `serverTime` 是**响应时刻的墙钟**（48 行），不是本批最后一条的 createdAt。两次拉取之间若产生超过 1000 条变更，本批只返回前 1000 条，而游标已越过剩余变更 → 剩余变更永远拉不到（90 天 cleanup 还会物理删除，sync.ts:155-162）。另：变更插入与 serverTime 同毫秒时 `createdAt > since` 也会跳过。
- 后果：多端数据永久不一致（脚本/api-smoke 与移动端均受影响；官方 UI 未使用 sync，风险面为外部客户端）。
- 建议：游标返回本批最大 `createdAt`（max(batch)），客户端用该值续拉；serverTime 与游标分离；pull 增加基于行 ID 的稳定排序。

### H3. 预约看板用 UTC 日期截断过滤：凌晨预约显示到前一天
- 文件：`src/web/AppointmentBoardPage.tsx:32-33`
- 场景：`String(row.startTime).slice(0, 10)` 取 ISO UTC 日期与 `<input type=date>` 的本地日期比较。诊所时区 +8，凌晨 0:00–7:59 的预约（如 8 月 5 日 07:30 → UTC 8 月 4 日 23:30）会被归到前一天。
- 后果：前台按日期看排班时漏看当天凌晨预约，可能造成椅位/医生排班误判（真实诊所高频场景）。
- 建议：用 `clock.clinicDate()`/本地时区格式化后再比较。

### H4. 分页参数非法 → 500 而非 400（已实测）
- 文件：`src/server/http/router.ts:33-34`，`src/server/infrastructure/repository.ts:66-67`
- 场景：`GET /api/v2/resources/patients?page=abc` 或 `pageSize=1.5` → `Number()` 得 NaN → `Math.max(1, NaN) = NaN` → LIMIT/OFFSET 绑定 NaN → better-sqlite3 抛 `SqliteError: datatype mismatch`（已用 better-sqlite3 实测确认）。
- 后果：客户端参数错误得到 500 "服务器内部错误"，而非 400 参数提示；错误被 errorMiddleware 归类为服务器故障。
- 建议：路由层校验 page/pageSize 必须为正整数，否则 400。

### H5. 微信发送失败原因被吞掉
- 文件：`src/server/application/service-modules/wechat.ts:60-63`（provider catch 全吞）、`111-113`（抛通用 ConflictError）
- 场景：网络错误、5s 超时、网关非 2xx、响应 JSON 解析失败，全部归约为 `network_error`/`http_xxx`，随后服务只抛"微信发送失败"，**不写任何日志**。
- 后果：诊所无法区分配置问题/网络问题/对方服务故障，排障无从下手；对用户提示也无法细化。
- 建议：provider 层记录原因（status、超时、错误消息）到日志与消息记录 result 字段；区分 4xx/5xx/超时三类错误映射不同提示。

### H6. 登录无审计、失败不进日志
- 文件：`src/server/http/app.ts:260`（公共路由注册在审计中间件 271 之前 → 登录请求不经过审计）、`src/server/http/middleware.ts:34`（errorMiddleware 只记 >=500）、`src/server/application/service-modules/auth.ts:44-75`（login 只更新 DB 计数）
- 场景：登录成功/失败均无 OperationLog；失败原因（密码错误/锁定/停用）不进日志（请求日志只有 statusCode，无用户名）。
- 后果：密码爆破、员工误操作无法审计追责；锁号/失败趋势只能查 DB 计数。
- 建议：登录成功/失败写审计（action=LOGIN_SUCCESS/LOGIN_FAILED，含 username/ip/traceId）；失败原因记 warn 日志。

## 三、中（Medium）

### M1. 幂等覆盖缺口（且空 requestId 直接跳过幂等）
- 文件：`src/server/infrastructure/idempotency.ts:28`（`if (!scope?.requestId) return fn();`）、`src/server/http/routes/workflow.ts`（appointments 创建/状态流转、wechat send/sendBatch、purchase receive、processing transition、followUp complete/batchComplete、bulk-import）、`src/server/http/router.ts:48-60`（通用资源 POST）
- 场景：① 未覆盖的操作（创建收费单、创建预约、通用资源新建、微信发送、采购收货、加工单流转、随访完成、批量导入）在请求超时后用户重试、双击、双端并发时重复执行；② 已覆盖的操作（charge.pay/refund、member recharge/consume/points、purchase-order.create、processing-order.create、inventory.transaction、debt.pay）若客户端不带 requestId（第三方/脚本调用），`withIdempotency` 直接短路，等于没有防重（官方 UI 均用 `crypto.randomUUID()`，不受影响）。
- 注：经核实不存在"空 requestId 命中旧 COMPLETED 响应导致第二单不执行"的情况——`idempotency.ts:28` 对空 requestId 直接跳过，旧假设已修正。
- 后果：重复收费单/重复预约/重复发送微信等；收费类操作靠"剩余金额"业务校验兜底，创建类无兜底。
- 建议：创建类操作服务端强制幂等（业务唯一键：收费单号、预约时间窗已部分防重）；批量发送用整批幂等键；文档要求第三方客户端必传 requestId。

### M2. logger.error 直接传 Error 对象 → 日志里是 `"error":{}`
- 文件：`src/server/infrastructure/logger.ts:50-61`、`src/server/main.ts:67,90,115,126`、`src/server/http/app.ts:112,141,154`、`src/server/scheduler.ts:42,64`
- 场景：`JSON.stringify(new Error(...))` 结果为 `{}`（已实测）。自动备份失败、审计 flush 失败、关闭 DB 失败等日志条目的 error 字段全部为空对象，message/stack 丢失。middleware.ts:35 显式取 message+stack 是唯一正确的样例。
- 后果：日志无法定位根因，等于关键故障信息丢失。
- 建议：日志层统一序列化 Error（message/stack/cause），或调用点改为传 `{ message, stack }`。

### M3. datetime 格式不强制：与 Z 格式混存破坏预约冲突检测
- 文件：`src/server/http/validation.ts:47-51`（只做 Date.parse）、`src/server/application/service-modules/auth.ts:465-481`（字符串比较 `startTime < ?`）、`src/server/infrastructure/clock.ts` 与 `src/domain/contracts.ts:22`（硬编码 +8）、`src/server/application/service-modules/operations.ts:320`（adherence 硬编码 '+8 hours'）
- 场景：官方 UI 用 datetime-local → `toISOString()`（Z 格式，一致）；但 API 客户端可提交任意可解析格式（`+08:00` 偏移、无时区等），与 Z 格式混存后，`assertNoConflict` 的字典序比较结果错误（如 `"2026-08-05T10:00:00+08:00"` 与 `"2026-08-05T02:00:00.000Z"` 实际同一时刻但字符串序不同）→ 冲突检测失效。
- 后果：医生/椅位双排预约；跨时区部署（诊所只在中国，+8 硬编码可接受，但格式混存无时区防护）。
- 建议：datetime 校验强制 `YYYY-MM-DDTHH:mm:ss.sssZ` 并统一归一化；冲突检测改用解析后数值或 SQLite datetime 函数。

### M4. 批量导入：逐行 catch 掩盖系统性错误 + 分片可部分提交
- 文件：`src/server/application/service-modules/clinical-ops.ts:121-167`
- 场景：每行 insert 失败被收集进 errors 继续（145-150 行），磁盘满/SQLITE_BUSY 等系统性错误被当成"该行数据问题"；每个分片独立 BEGIN/COMMIT（143-153 行），若某分片 COMMIT 失败 → 整个请求 500，但前面分片已提交 → 用户重试会重复导入前面分片。
- 后果：库存/患者数据部分重复或部分丢失；磁盘满时用户看到"导入成功 N 失败 M"，归因错误；errors 数组含原始 SQL 消息。
- 建议：区分业务行错误（继续）与系统性错误（中止整个导入并回滚）；整批单事务或导入 job 记录已完成行数支持续传。

### M5. 备份失败遗留 .tmp、恢复后遗留 staged 文件
- 文件：`src/server/application/service-modules/backup.ts:50`（tempPath `.tmp`）、`backup.ts:110-144`（`.staged-*`）、`src/server/infrastructure/restore-apply.ts:42-45`（拷贝后不删 staged 文件）
- 场景：create() 中途失败（磁盘满、加密失败）遗留 `.tmp`；applyStagedRestore 把 staged 文件拷为正式库后不删除 staged 文件。`list()` 过滤掉这两类（backup.ts:30-32），cleanup() 也不删。
- 后果：备份目录磁盘空间缓慢泄漏（staged 文件可能数百 MB），诊所磁盘被悄悄填满。
- 建议：create 失败 finally 清理 .tmp；恢复应用成功后删除 staged 文件；cleanup 顺带清理 `.tmp`/`.staged-*`。

### M6. 审计缓冲 flush 失败即丢失，且无告警
- 文件：`src/server/http/app.ts:101-157`
- 场景：auditBuffer 批量落库失败仅记日志（112 行），审计行直接丢弃；shutdownFlushAudit 只挂在 SIGINT/SIGTERM（158-159 行），Electron 强杀进程（main.cjs:259 `processToStop.kill()`）时可能不触发。
- 后果：操作审计（合规要求）静默缺失。
- 建议：flush 失败重试/降级同步写；创建告警；shutdown 时通过 IPC 'shutdown' 消息确保 flush（main.ts:133-135 已支持消息关闭，可复用）。

## 四、低（Low）

### L1. CSV 导出无公式注入防护
- 文件：`src/server/http/router.ts:139-161`（csvCell）
- 场景：导出字段以 `=`、`+`、`-`、`@` 开头（如备注文本）时，Excel/WPS 打开会按公式执行（如 `=HYPERLINK(...)`）。
- 建议：对以 `=+-@` 开头的单元格加前缀 `'` 或 `\t`。

### L2. ChargeService.create 金额乘法可溢出
- 文件：`src/server/application/service-modules/financial.ts:89`（`Math.round(item.price * item.quantity)`）
- 场景：price/quantity 只校验 `Number.isSafeInteger` 且 >0（无上限），两者乘积超过 2^53 时精度丢失（如 9e15 × 9e15），金额以 REAL 浮点存储。需恶意/损坏客户端触发，官方 UI 不可能。
- 建议：校验 `price * quantity` 不超过安全上限（如 1e12 分）并拒绝。

### L3. 搜索服务层对空查询抛 FTS5 语法错误（路由已拦截）
- 文件：`src/server/application/read-services.ts:134-138`，`src/server/http/read-routes.ts:117-121`
- 场景：`MATCH ''` 实测抛 `fts5: syntax error`（已用真实 FTS5 验证）。当前路由层 `q.length < 2` 先返回空（118-120 行）所以不可达；仅直接调用服务或未来新路由会触发 500。
- 建议：search() 内对空 ftsQuery 直接返回 []。

### L4. 预约看板固定取前 200 条
- 文件：`src/web/AppointmentBoardPage.tsx:30` + `src/server/infrastructure/repository.ts:67`（上限 200）
- 场景：诊所预约总量 >200 且当天预约不在按 createdAt 倒序的前 200 条内时，看板漏显示（多为历史大诊所）。
- 建议：看板按日期先过滤再分页，或服务端按日期查询。

### L5. 若干英文错误消息未翻译
- 文件：`src/web/messages.ts`（翻译表）
- 场景：`Insufficient permissions`（middleware.ts:88 的 403）等少数消息不在 translations 表，friendlyError 回退原英文；同步 push / 批量导入 errors 数组内的原始 SQL 消息（如 `UNIQUE constraint failed: ...`）也会直出给 API 客户端（当前 UI 只 toast 计数，不显示明细）。
- 建议：补齐翻译；错误码化并统一中文映射。

### L6. 请求日志无 userId/clinicId
- 文件：`src/server/http/app.ts:232-244`
- 场景：请求日志只有 traceId/method/path/statusCode，无操作人维度；排查"谁在什么时候做了什么"需另查审计表。
- 建议：请求日志带上 userId/clinicId（审计中间件已有 context，可复用）。

## 五、Top 5 最容易在真实诊所触发的事故场景

1. **老诊所升级/换机后应用永远打不开（迁移 116 崩溃循环）**
   现有 v1 数据中只要存在负数会员余额、0 金额退款、重复卡号、孤儿外键之一，升级后每次启动都失败并无限重启（C1 + H1 叠加：窗口不出现、提示误导）。这是最可能真实发生且最致命的一条——数据越"脏"，越打不开。

2. **欠费还款时账不平（DebtService.pay 非原子）**
   欠费收款是诊所日常高频操作，任何一次第二步写库失败（磁盘忙、机器卡顿、SQLITE_BUSY）都会造成"钱收了、收费单没平"，且重试被剩余金额校验挡住，只能人工对账修数据（C3）。

3. **凌晨预约在看板上显示到前一天**
   前台每天早上打开预约看板排班，0–8 点的预约（复诊、种植手术常约早班）全部显示在错误日期，直接导致漏排/双排（H3）。

4. **恢复备份流程把应用搞死且无法自愈**
   员工点"恢复备份"后重启，若 staged 文件被清理或路径异常，应用进入无限重启、无窗口状态；提示语还是"检查端口占用"，IT 只能手动删 marker（C2 + H1）。

5. **微信批量通知失败但完全查不到原因**
   诊所做随访/营销群发时，微信通道网络波动即整批失败（每条约 5s 超时），用户只见"微信发送失败"，日志无原因、无区分，且 sendBatch 无幂等，重试可能重复发送（H5 + M1）。
