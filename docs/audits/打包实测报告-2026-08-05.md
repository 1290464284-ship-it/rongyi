## 2. 修复前 FAIL 证据（打包版）

1. **受保护 IPC 全部被拒（Untrusted IPC sender）**：修复前 `TRUSTED_RENDERER_PATTERN` 仅匹配 `file://...dist-web/index.html`（无后缀）与 `http://localhost:5180/`（无后缀）。渲染器经 HashRouter 导航后 URL 恒为 `file://.../dist-web/index.html#/patients`，登录页即被拒；项 3A 首次实测 `desktop.checkUpdates()` 直接 reject `Untrusted IPC sender`。
2. **BUG#2 token 持久化从未成功**：`secretPath()` 字符集 `/^[a-zA-Z0-9_-]{1,64}$/` 不允许点号，而白名单 key 为 `v2.token`/`v2.refreshToken` → 每次 `get/set/delete` 都抛 `Invalid secret key`（被调用方 catch 吞掉，返回 null/false）。铁证链：`probe-set.cjs`（set 返回 false 但无异常）→ `probe-patch.cjs`（打补丁观察 `Set.prototype.has`：`v2.token` 被判允许、`isEncryptionAvailable` true、但 `encryptString` 从未被调用）。**结论：自 HEAD 起 safeStorage 令牌持久化形同虚设，每次启动必须重登**——与 IPC、环境变量均无关。
3. **BUG#3 签名校验必然 TypeError**：`main.cjs` 原代码 `if (win32) autoUpdater.verifyUpdateCodeSignature = true;` 把 NsisUpdater 的 getter/setter（包装 `windowsExecutableCodeSignatureVerifier.verifySignature`）覆盖成布尔 → 下载完成进入校验阶段必然抛 `this._verifyUpdateCodeSignature is not a function`。场景 B 修复前实测即命中该 TypeError。
4. **BUG#4 错误窗重试从未生效**：`error.js` 首行 `const { desktop } = window;` 与 `contextBridge.exposeInMainWorld('desktop', ...)` 在页面全局作用域重复声明同名词法绑定 → 必然 `SyntaxError: Identifier 'desktop' has already been declared`（渲染器 pageerror 实测确认）→ msg 永不填充（永远显示「正在加载错误信息…」）、重试/退出按钮 onclick 为 null。项 5 修复前实测 FAIL：错误窗出现后 30s 重试无任何反应。

## 3. 修复 diff（apps/v2/electron/main.cjs，共 4 处，全部带 T2R-22 注释）

### 修复 ① TRUSTED_RENDERER_PATTERN 放宽（R2-P1-15 盲区实证）

```diff
-const TRUSTED_RENDERER_PATTERN = /(^file:\/\/.*dist-web[\\/]index\.html$)|(^http:\/\/localhost:5180\/?$)/;
+// T2R-22: 渲染器经 HashRouter 导航后 URL 恒带 #/... 片段（dev 下还有 ?/ # 查询），
+// 错误窗经 loadFile 带 ?msg= 查询串；这些都属于同文档导航，不引入新来源，
+// 因此放行 [?#] 后缀并显式放行 error.html，否则受保护 IPC 全部被误拒。
+const TRUSTED_RENDERER_PATTERN = /(^file:\/\/.*dist-web[\\/]index\.html(?:[?#].*)?$)|(^file:\/\/.*error\.html(?:[?#].*)?$)|(^http:\/\/localhost:5180\/?(?:[?#].*)?$)/;
```

**论证**：`[?#]` 后缀均来自同一文档的同文档导航（HashRouter 片段 / loadFile 查询串），不引入新来源；`error.html` 是错误窗（重试/退出必须能调受保护 IPC）；正则保持 `file://` 前缀 + 路径收尾约束，不放大攻击面。R2-P1-15 属盲区：受保护 IPC 的信任边界逻辑在纯 CJS `main.cjs` 中，仓库 582 个测试无一覆盖（TS 侧无 Electron 主进程测试），只能打包实测暴露。

### 修复 ② secretPath 正则放行点号（BUG#2）

```diff
-  if (!/^[a-zA-Z0-9_-]{1,64}$/.test(key)) throw new Error('Invalid secret key');
+  // T2R-22: 白名单 key 形如 'v2.token' / 'v2.refreshToken'（含点号），原字符集
```

### 修复 ③ 删除 verifyUpdateCodeSignature 布尔赋值（BUG#3）

```diff
-if (process.platform === 'win32') {
-  autoUpdater.verifyUpdateCodeSignature = true;
-}
+// T2R-22: 不要给 verifyUpdateCodeSignature 赋布尔值！NsisUpdater 把它实现为
+// getter/setter（包装 windowsExecutableCodeSignatureVerifier.verifySignature），
```


## 6. 遗留清单

1. **CI 冒烟链路不可用（脚本级）**：`v2-windows-smoke.yml` 36-37 行调用 `electron:pack`（`--dir`，不产安装包 exe），56 行依赖 `release-v2/` 下的安装包（被 `.gitignore` 排除，CI 检出不存在）——CI 无法产出/引用安装包做冒烟。另 `installer:smoke`/`upgrade:smoke` 脚本依赖本地已有安装包，需人工先 `electron:dist`。
2. **线上更新签名校验实际未启用**：仓库 `app-update.yml`（打包模板）无 `publisherName`，electron-updater 读到 null 时静默跳过签名校验；场景 B 证明配置 `publisherName` 后能拦截伪造包（`ERR_UPDATER_INVALID_SIGNATURE`），但线上配置未启用，属于「能力就绪、配置缺位」。
3. **3199 端口环境阻塞**：本机 Windows 保留端口范围 3170-3269（Hyper-V/WSL 动态端口）覆盖 3199 → 两个冒烟脚本硬编码 3199 必然 `listen EACCES`（已实测复现）。本次以脚本副本（仅端口 3199→4199，仓库零改动）完成全流程验证；CI 环境需避开保留范围或脚本改用动态端口。
4. **safeStorage/环境异常健壮性缺陷**：`getOrCreateSecret` 解密失败会把密文当明文返回 → spawn 环境变量含 NUL 字节 → 错误窗循环风险（gui-ud 毒化实证）。建议后续版本在解密失败时删除重生成并显式报错。
