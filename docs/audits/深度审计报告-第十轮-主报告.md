## 本轮新发现

### H-01 SyncChange 同步队列覆盖不完整（高）

离线同步依赖 `SyncChange` 全量覆盖所有写路径，但大量“直写 SQL”的业务路径只维护了搜索索引，没有调用 `recordSyncChange`：

- `appointment.service.ts`：临时患者建档、预约创建与状态变更（Patient / Appointment）
- `treatment-plan-billing.ts`、`prescription-process.ts`、`charge-tree.ts`：创建 Charge
- `follow-up.repository.ts`：FollowUp 创建与完成
- `purchase-order.repository.ts`：采购单创建与收货
- `refund-flow.ts`：退款冲销时的 Charge 更新
- `triage.ts`：预约改期
- `dispense.ts`、`inventory-batch.ts`、`stocktake.ts`、`inventory-docs.ts`、`high-value.ts`：InventoryItem 库存/字段变更

全仓只有 21 处 `recordSyncChange` 调用，且没有任何 spec 断言“上述业务写路径后 SyncChange 必有一条记录”。第八轮修复的 `ChargeRepository` 只是其中一条路径；离线设备会静默漏掉预约、收费、随访、采购、库存变更。

建议：建立统一写入门面（例如 repository/unit-of-work 层强制发同步事件），并新增“每条受支持业务写路径 → SyncChange 行数 +1”的回归测试。

### H-02 多诊所成员关系与 User.clinicId 语义不一致（高）

第九轮迁移 153 把 `UserRole` / `UserPermission` 改为按 `clinicId` 复合主键，权限和登录已优先走 `UserClinic`，但以下路径仍按 `User.clinicId` 做租户过滤：

- `auth.service.ts:259` `listDoctors`
- `common.ts:114` `assertDoctorExists`
- `dispense.ts:72` 医生校验
- `shift-template.ts:156` 用户校验
- `triage.ts:71` 医生校验
- `auth.service.ts:390/417/432` `updateUser` / `resetPassword` / `deleteUser`

后果：一个医生被加入诊所 B 但 `User.clinicId` 仍指向诊所 A 时，登录和权限没问题，但在诊所 B 无法被选为医生、无法排班、无法分诊，BOSS 也无法在诊所 B 管理该用户。

建议：医生/用户查询统一改为 `UserClinic` 成员关系；`User.clinicId` 只保留为“当前/默认诊所”展示字段。

### H-03 资金与库存并发写缺少原子守卫（高，多进程场景）

单进程内 better-sqlite3 同步执行不会交错，但项目声称支持多实例/多进程共享 SQLite，且 `multi-instance-smoke` 只并发建患者，未覆盖资金与库存：

- `ChargeService.pay/refund`：`findById` 在事务外读余额，`updatePayment/updateRefund` 无条件写回（charge.service.ts:198 / 305 / 318）
- `DispenseService.dispense`：库存先校验再 `UPDATE InventoryItem SET stock = ?`，UPDATE 未带 `stock >= ?` 守卫（dispense.ts:296-307）
- `InventoryBatchService.consumeFifo/create`：批次余量减扣无原子守卫（inventory-batch.ts:281-289 / 121-139）
- `PurchaseOrderService.receive`：库存累加基于事务内先读后写（purchase-order.service.ts:102-131）

多进程并发时可能出现 `SQLITE_BUSY_SNAPSHOT`（表现为 500）或静默覆盖；批次扣减还可能扣成负数。建议所有扣减改为 `UPDATE ... WHERE stock >= ?` / `remainingQuantity >= ?` 并检查 `changes`，或统一 `BEGIN IMMEDIATE`。

### M-01 管理员重置密码不清除锁定状态（中）

`resetPassword`（auth.service.ts:415-424）只改密码并 bump tokenVersion，不重置 `loginAttempts` / `lockedUntil`。正常锁定最长 60 秒影响不大；但 `lockedUntil` 一旦损坏（NaN），登录侧按 fail-closed 永久视为锁定，且没有任何 UI 路径可解除。

建议：`resetPassword` 同时清零 `loginAttempts`、`lockedUntil`。

### M-02 预约改期端点缺少医生/椅位/时间区间校验（中）

`TriageService.rescheduleAppointment`（triage.ts:136-183）：

- 不校验新 `doctorId` / `chairId` 是否存在
- 不校验冲突（医生/椅位是否已被占用）
- 不校验 `endTime > startTime`
- 不维护 SyncChange

拖拽改期可以产生“幽灵医生/椅位”和双重预约。

### M-03 快捷划价缺少 visit/doctor 引用校验（中）

`ChargeTreeService.quickCharge`（charge-tree.ts:77-173）直接写入 `visitId` / `doctorId`，未像 `ChargeService.create` 一样做存在性与归属校验，可能产生孤儿引用；同时未写 SyncChange。

### M-04 审计脱敏深度上限可绕过（低-中）

`maskSensitiveFields` 深度超过 5 后原样返回（security.ts:86-93），通用资源审计中间件把原始 `req.body` 递归脱敏后写 OperationLog（app.ts:202-203）。深度超过 5 的嵌套 `password` / `token` 等键名不再被掩码。

建议：超过深度时递归展开为 `'[MaxDepth]'` 而不是原样返回。

### M-05 三套通用 CRUD 页面仍并存（低）

`CrudPage`、`ResourcePage`、`SimpleListPage` 继续共存，`SimpleListPage` 只服务 5 个统计 Tab。README 已写明选择规则，但列表/表单/导出逻辑仍有三份实现，属于已知的结构性重复。

### M-06 文档与日志仍有少量过期数字（低）

`apps/v2/README.md:215` 写“170 个测试文件”，本轮实测 171 个文件 / 1512 个用例；第九轮报告也自认日志与文档仍存在过期数字。
