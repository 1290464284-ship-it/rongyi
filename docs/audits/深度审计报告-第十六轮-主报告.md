## 2. 后端重点发现（P1）

1. 临床工作流状态机仍是先读状态、再无条件 `UPDATE`，不检查 `changes`；多实例下 `IN_PROGRESS -> COMPLETED` 与 `IN_PROGRESS -> CANCELLED` 可同时“成功”。已修复：`updateStatus` 支持 `fromStatus` 条件 + `changes` 校验，挂号迁移合并为单次条件更新并在同一事务内创建 Visit。
2. 病历修改申请 `requestEdit/review` 先检查后无条件更新，并发可覆盖 PENDING。已修复：`editRequestStatus` 条件更新 + `changes` 校验。
3. 补货建议应用到采购单时更新无 `OPEN` 条件，两个进程可对同一批建议各建采购单。已修复：`status OPEN/NULL` 条件更新 + `changes=0` 抛 `ConflictError`。
4. 发药单编辑/删除只在事务外检查 `PENDING`，事务内更新/软删无状态条件。已修复：事务内 `status='PENDING'` 条件 + `changes` 校验。
5. 债务还款只更新 `Debt/Charge`，未写 `PaymentLedger`，账务流水缺失。已修复：复用 `recordPaymentLedger` 落 `PAY/DEBT` 流水。
6. 会员卡积分扣减无 `points + ? >= 0` 守卫，并发可扣成负数。已修复：仓储条件更新 + `ConflictError`。
7. 退款驳回/取消的冲销用快照绝对写 `refundedAmount/balance/paidAmount`，并发可能互相覆盖。已修复：改为条件相对更新（`refundedAmount - ? WHERE refundedAmount >= ?` 等）+ SQL CASE 状态。

## 3. 后端重点发现（P2）

- 预约创建只 `Date.parse` 校验，未归一化 ISO，字符串比较冲突可能漏判。已修复：统一 `toISOString()` 后落库与查冲突。
- 首诊重启接受客户端 `doctorId` 但未校验医生归属。已修复：`assertDoctorExists`。
- 收费组合列表逐 combo 查明细（N+1）。已修复：按 `comboId IN (...)` 批量加载分组。
- 分诊改期 `UPDATE Appointment` 无状态条件，并发取消后仍可改期。已修复：`status NOT IN ('CANCELLED','NO_SHOW')` + `changes` 校验。
- 退款分页服务层 NaN 未校验（路由层有兜底）。已修复：`Number.isFinite` 校验。
- `PAY_METHODS` 与领域 `PayMethod` 重复维护。已修复：直接复用领域枚举。
- 数量上界不一致（批次 10 亿 vs 单据/发药无上界）。已修复：退回/库损/调拨与发药统一 `<= 1_000_000_000`。

保留未修（需架构或产品决策）：
- `sync.ts` 显式 `BEGIN` 内 `await` repository 调用，依赖微任务串行与写队列兜底；需统一连接级串行队列或事务内零 await。
- `processing-flow.setStep` 手动改状态无“从何状态”条件；当前产品语义允许任意改，保留现状并在报告登记。

补充已修复（第二批）：
- `charge-combo` 目录价格 TOCTOU：`ChargeService.create` 支持 `catalogId`，开单事务内复验目录价。
- 幂等 async 已知业务错误（校验/冲突/未找到）删除 PROCESSING 供重试；未知错误仍保留防重。
- refresh token 数据库级 claim（IdempotencyRecord `auth.refresh`），多实例共享轮换会话；注销/吊销同步清理。
- 微信提醒迁移 156：先去重再加 `(clinicId, patientId, scene, scheduledDate, sourceId)` 部分唯一索引。

## 7. 你问我答

### 7.1 我遗漏了什么

- 只派出 2 路子代理，结构/发布没有独立子代理复核，靠本地扫描补位。
- 未做真实浏览器无障碍树/截图验证，`inert` 行为只有单测与代码依据。
- 未对保留项（sync 事务、refresh 多实例、幂等语义）做跨进程实测，只做了代码路径分析。
- 没有逐条给全部 P3 补测试。

### 7.2 你（用户）遗漏了什么

- 没有定义“编辑保存半套数据”可接受的失败语义：是回滚、重试还是只读校验。
- 没有定义多实例 refresh 并发策略：允许短期会话族吊销，还是必须数据库级 claim。
- 没有定义 ResourceHub 深链 Tab 的默认行为。
- 没有为微信提醒唯一性给出业务键口径。

### 7.3 我最害怕什么

最怕“账面上成功、数据里丢失/错位”：退款冲销并发覆盖、债务还款缺流水、病历跨患者误关联、删除父记录留下孤儿明细。这些要么不可逆，要么只能靠事后对账发现。本轮已把其中可落地的条件更新、归属校验、失败中止、跨实例 refresh claim 与微信提醒唯一约束全部补上。

### 7.4 技术风险

- 多实例并发下“条件更新 + changes 校验”已覆盖本轮可落地路径；保留项集中在 sync 事务零 await。
- 前端编辑保存仍是多请求拼装，无服务端事务边界。
- 工作台分页后默认只显示首页，长列表用户需要翻页（已提供分页器）。
- `inert` 依赖现代 Chromium，Electron 43 支持；浏览器 dev 模式不受影响。
