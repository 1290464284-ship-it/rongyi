# v2 口腔诊所系统性能审计报告（面向 10 万患者场景）

日期：2026-08-05 | 方法：代码审查（所有问题核对到 文件:行号）+ 真实/临时库实测（Windows 11 / node v24 / NVMe）。只报告验证过的内容。

实测基线：dev 库仅 65 患者（负载冒烟 p95 16.4ms 通过）；benchmark 临时库 100k 患者+100k 收费：插入 983/863ms、FTS 搜索 7ms、dashboard 65ms；integrity_check 100k+100k 行 = 535ms（quick_check 170ms）。

## 严重（S）

### S1. FTS5 触发器写放大，成本随库规模二次增长 — migrations.ts:293-353（19 个触发器，如 L303 `DELETE FROM SearchIndex WHERE resource=… AND recordId=…`）
- SearchIndex 的 resource/recordId/clinicId 均为 UNINDEXED 列（L294-296），触发器里非 MATCH 的 DELETE 必须逐行扫描整个 FTS 表再 INSERT，每写一行代价 ∝ FTS 总行数。
- 触发：所有患者/收费/预约/库存/供应商/回访的增改删。
- 量化（实测）：FTS 10k 行时 0.86ms/行（患者）、2.1ms/行（收费）；200k 行时 35.6ms/26.5ms（无触发器 0.008/0.005ms，放大 4000 倍+）。外推 50 万收费单笔 ≈130ms，同步阻塞请求线程；带触发器批量导入 10 万收费 ≈210 秒（无触发器 863ms）——这正是 benchmark 必须先 DROP 触发器的原因。
- 建议：删触发器改「零成本写入 + 定时批量重建」（实测回填 200k 行仅 692ms，索引延迟数分钟可接受）；或迁到 FTS5 external-content/contentless 模式按 docid 删除。

## 高（H）

### H1. 仪表盘/经营分析全表聚合，无预聚合无服务端缓存 — read-services.ts:16-24（dashboard 6 子查询）、:59-65（revenue）、:84-90（patientGrowth）；analytics.ts:30-72（clinicOverview 7 CTE）、:79-90（frequentItems）；core.repositories.ts:605-655（rfm/churn/doctorAnomalies）；路由无缓存（read-routes.ts:29,68）；前端 AnalyticsDashboardPage.tsx:77-98 挂载即 6 并行查询
- dashboard 100k 收费 = 65ms，线性增长 → 100 万收费 ≈0.6-1s，且同步阻塞全部请求。
- 建议：日聚合表 + 后台增量维护；服务端 TTL 缓存；strftime 分组无法走索引。

### H2. 搜索 `LIKE '%term%'` 全表扫 + 击键即查无防抖 — repository.ts:88-93（前置通配符无法用 (clinicId,name) 索引）、:96（COUNT 全扫）、:101（SELECT *）；PatientsPage.tsx:75,83-86,240-241（onChange 直接发 `?search=`）
- 10 万患者时单次击键 ≈50-150ms；5 键/秒打字 → 事件循环 0.3-0.7s/秒被占满，全系统卡顿。
- 建议：300ms 防抖；改用已有 FTS5（实测 7ms）或前缀匹配 + 最小列。

### H3. 幂等清理每次写请求全表 DELETE — idempotency.ts:32-33（L33 `status != 'COMPLETED' AND updatedAt <= ?` 无索引，实测表无 (status,updatedAt) 索引；L32 有 expiresAt 索引可用）
- 表规模≈24h 写量；日写 5k 时 1-5ms/写，日写 1 万+ 时 10ms+/写。
- 建议：加 `(status, updatedAt)` 索引；清理移入定时任务。

### H4. 启动 integrity_check 挤占 Electron 15s 健康窗口 — database.ts:310-312（每次启动全库校验）；main.ts:55-62（restore→建库→迁移→seed→listen 全同步）；electron/main.cjs:120-139（waitForApi 15s）
- 100k+100k 行 535ms（NVMe）；100 万行 ≈5s+，机械盘/云盘 15-25s，可触发重启循环；quick_check 仅 170ms。
- 建议：默认 quick_check，异常退出才全量校验；FTS 回填后置；Electron 超时放宽。

### H5. 前端无代码分割 — hub-tabs.tsx:1-35（34 页面静态导入，无 lazy）；vite.config.ts 无 manualChunks；产物单文件 414KB
- 低端机白屏 200-500ms，随页面增长恶化。

## 中（M）

- M1 tenant.ts:19 `(clinicId = ? OR clinicId IS NULL)` 削弱所有复合索引前缀 → legacy 数据补齐后改用已存在的 tenantWhereStrict（L23-27）。
- M2 SystemOperationsPage.tsx:47-49 全局搜索（FTS5 快，7ms）但每键触发无防抖 → 300ms 防抖。
- M3 sync.ts:73-122 push 逐条写库无事务、无批上限 → 1000 条 ≈0.1-0.6s 且无原子性；包事务+限 500/批。
- M4 replenishment.ts:18-20,46-82 全表 SELECT * + 逐条 INSERT 无事务 → 500 建议 ≈0.1-0.5s；包事务。
- M5 analytics.ts:79-90 frequentItems 按 (category,name) 分组无索引（实测 ChargeItem 仅 chargeId/clinicId 等索引）→ 30-50 万行全扫 100-300ms；加 (clinicId,category,name) 索引。

## 低（L）

- L1 repository.ts:194-207 每 insert/update 逐 relation 字段 SELECT（点查 ≈0.01ms，批量导入累计）。
- L2 wechat.ts:120-126 批量发送串行 HTTP、单条失败中断整批（500×50ms=25s）→ allSettled+并发≤10。
- L3 auth.ts:474-482 预约冲突 OR 查询（10 万预约 ≈10-50ms/次）→ 拆两条查询。
- L4 app.ts:136-140 审计超 50 条同步事务刷写（实测 50 条 INSERT <1ms，可忽略）。
- L5 files.ts:41 上传同步 writeFileSync（20MB ≈20-100ms 阻塞）；ChargesPage.tsx:63-65 患者下拉 200 条全字段。

## 10 万患者 Top 5 风险

1. FTS 触发器写放大（S1）——每笔收费 27-36ms 且二次增长（50 万收费时 ≈130ms/笔，同步阻塞收银台）；批量导入从 1 分钟级恶化到数小时级。最先处理。
2. 患者搜索击键即查 + LIKE 全表扫（H2）——打字时事件循环饱和，前台全部卡顿。
3. 仪表盘/经营分析全表聚合（H1）——65ms@100k → 1s@100 万收费，高峰看板刷新全局劣化。
4. 启动 integrity_check 逼近 15s 窗口（H4）——100 万行+慢盘 15-25s，Electron 重启循环，单机不可用。
5. 幂等清理全表 DELETE（H3）——日写 5k-1 万时每次写多付 5-10ms；叠加 S1 后单笔收费总开销 40-140ms。

## 排除项（已验证无问题）

备份链路安全（SQLite Online Backup API / VACUUM INTO）；Charge/Treatment/OperationLog/Appointment/UsedRefreshToken/SyncChange 索引齐全（实测 sqlite_master）；FTS 搜索读路径健康（7ms）；审计缓冲设计合理；前端 lucide-react 可摇树、React Query 30s/5min 配置合理。
