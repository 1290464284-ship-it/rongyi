# v2 口腔诊所系统性能审计报告（面向 10 万患者场景）

- 审计对象：`D:/Desktop/rongyi/apps/v2`（Electron + React + Express + better-sqlite3，约 3 万行 TS）
- 审计日期：2026-08-05
- 方法：代码审查（全部问题均核对到 `文件:行号`）+ 真实库/临时库实测（本机 Windows 11，node v24.18.0，NVMe）
- 原则：只报告实际验证过的内容；文中所有耗时均为实测值或基于实测的线性外推

## 一、严重（S）

### S1. FTS5 全文索引触发器：每次写操作全表扫描 SearchIndex，成本随库规模二次增长
- **位置**：`src/server/infrastructure/migrations.ts:293-353`（SearchIndex 虚拟表 L293-298；Patient 触发器 L302-352，InventoryItem L355-377、Supplier L378-400、Appointment L401-425 及 Charge/FollowUp 同类触发器共 19 个）
- **问题**：每个写触发器先执行 `DELETE FROM SearchIndex WHERE resource = '…' AND recordId = NEW.id`（L303、L312、L321…）。SearchIndex 的 `resource/recordId/clinicId` 均为 `UNINDEXED` 列（L294-296），该 DELETE 不是 FTS5 MATCH 查询，**必须逐行扫描整个 FTS 表**；随后再 INSERT 新行。因此每写一行代价 ∝ FTS 表总行数（二次增长）。
- **触发条件**：任何患者/收费/预约/库存/供应商/回访的 INSERT 或 UPDATE（含软删除），即所有业务写操作。
- **量化预估（实测）**：
  - FTS 10k 行时：患者 0.86ms/行、收费 2.1ms/行（无触发器 0.008/0.005ms/行 → 放大 104–405 倍）；
  - FTS 200k 行时（≈10 万患者+10 万收费）：**患者 35.6ms/行、收费 26.5ms/行**（放大 4000 倍以上）；
  - 外推：50 万收费时单次收费写入 ≈130ms、100 万收费时 ≈260ms，且是同步阻塞在请求线程（better-sqlite3 同步 API）；
  - 批量导入：带触发器插入 10 万患者 ≈86 秒、10 万收费 ≈210 秒（无触发器仅 983ms/863ms，即 benchmark 必须先 DROP 触发器的原因）。
- **建议**：放弃逐行维护，改为「写入零成本 + 定时批量重建」：删除全部触发器，夜间/空闲任务执行 `INSERT INTO SearchIndex SELECT … FROM Patient/Charge/…`（实测回填 200k 行仅 692ms），搜索索引允许延迟数分钟；或改用 FTS5 external-content / contentless 模式，让触发器按 docid 精准删除（需迁移既有索引，工作量中等）。短期兜底：触发器内 DELETE 改为先按 recordId 收集 rowid 再删除（FTS5 的 `WHERE SearchIndex MATCH 'recordId:"…"'` 仍不解决），最直接是立即上线定时重建方案。

## 二、高（H）

### H1. 仪表盘/经营分析：全表聚合、无预聚合无缓存，每次进页面全量重算
- **位置**：`src/server/application/read-services.ts:16-24`（dashboard 6 个关联子查询）、`read-services.ts:59-65`（revenue）、`read-services.ts:84-90`（patientGrowth）；`src/server/application/service-modules/analytics.ts:30-72`（clinicOverview 7 个 CTE 全表扫）、`analytics.ts:79-90`（frequentItems）；`src/server/infrastructure/repositories/core.repositories.ts:605-620`（rfm）、`623-638`（churn）、`641-655`（doctorAnomalies）；路由无缓存（`src/server/http/read-routes.ts:29,68`）。
- **问题**：COUNT/SUM 全表扫 + `strftime()` 分组（函数包裹列，无法走索引）。前端 `AnalyticsDashboardPage.tsx:77-98` 挂载即 6 个查询并行、`DashboardPage.tsx:16-18` 挂载即查，只有全局 30s staleTime（`src/web/main.tsx:13`），无服务端缓存。
- **触发条件**：打开首页仪表盘、经营分析页、诊所总览（BOSS）、客户价值/流失分析页；每次进入（30s 内重复进入有 React Query 缓存）。
- **量化预估（实测）**：dashboard 100k 患者+100k 收费 = 65ms，线性增长 → 100 万收费 ≈0.6-1s；revenue/patientGrowth 的 strftime 全扫 10 万行 ≈30-80ms/查询；clinicOverview 7 表全扫跨全诊所（100k 数据 ≈100-200ms）。better-sqlite3 同步执行，一个慢查询阻塞全部请求。
- **建议**：建日聚合表（按 clinicId+日期存患者/收费/预约/随访计数与金额），由写入路径或后台任务增量维护，查询只读聚合表；dashboard 加服务端 TTL 缓存（60s）；clinicOverview 仅 BOSS 低频使用可接受但建议缓存。

### H2. 列表搜索 `LIKE '%term%'` 全表扫 + 前端击键即查、无防抖
- **位置**：`src/server/infrastructure/repository.ts:88-93`（LIKE 前置通配符 + OR 多字段）、`:96`（COUNT(*) 全扫）、`:101`（SELECT *）；`src/web/PatientsPage.tsx:75,83-86,240-241`（onChange 直接 setSearch → 每次击键发 `?search=` 请求）。
- **问题**：`%term%` 无法使用 Patient 的 `(clinicId, name)` 等索引；每次击键 = COUNT 全扫 + SELECT 全扫两趟，且 SELECT * 拉全字段（含 JSON 列反序列化）。
- **触发条件**：患者列表页搜索框打字（最常用功能之一）。
- **量化预估**：10 万患者时单次击键 ≈50-150ms（全表 LIKE + 字符串匹配 + JSON 解析）；按 5 键/秒打字 → 事件循环约 0.3-0.7s/秒被占满，期间所有其它请求排队；删除/编辑弹窗搜索（PatientsPage.tsx:130）同样全扫。
- **建议**：前端 300ms 防抖 + 最小长度 2；后端改用已有 FTS5 SearchIndex（`/api/v2/search` 已存在，实测 7ms）或至少改前缀匹配 `LIKE 'term%'`（可走 (clinicId,name) 索引）+ 仅 SELECT 所需列；COUNT 结果可缓存/降级。

### H3. 幂等清理：每次写请求先全表 DELETE 扫描
- **位置**：`src/server/infrastructure/idempotency.ts:32-33`
- **问题**：每个带幂等键的写请求先执行两条 DELETE：L32 走 `expiresAt` 索引（可接受）；L33 `status != 'COMPLETED' AND updatedAt IS NOT NULL AND updatedAt <= ?` **无任何索引**，全表扫 IdempotencyRecord（表无 (status, updatedAt) 索引，见实测索引清单）。
- **触发条件**：所有带幂等键的写请求（每次收费/预约/患者创建的默认路径）。
- **量化预估**：表规模 ≈ 24h 内写请求数（TTL 24h 且 L32 只清已过期行）。10 万患者场景每日 2-5 千笔写 → 全扫 5k 行 ≈1-5ms/写；若日写量 1 万+ → 10ms+/写，且随日写量线性恶化。
- **建议**：`CREATE INDEX idx_idempotency_status_updated ON IdempotencyRecord(status, updatedAt)`；或将两条清理移入每日定时任务，写路径只保留单条 key 点查。

### H4. 启动时序：integrity_check + 迁移/FTS 回填 挤占 Electron 15s 健康检查窗口
- **位置**：`src/server/infrastructure/database.ts:310-312`（每次启动 `integrity_check`）；`src/server/main.ts:55-62`（restore→createDatabase→syncLegacySchema→migrations→seed→listen 全同步）；`electron/main.cjs:120-139`（waitForApi 15s 超时，500ms 轮询 /health）。
- **问题**：启动即对全库做完整性校验（全库 B-tree 扫描），叠加迁移与 FTS 回填，均在 listen 之前完成；超 15s 即被 Electron 判定失败并重启，重启又跑一遍 → 启动循环风险。
- **量化预估（实测）**：100k+100k 行 integrity_check = 535ms（本机 NVMe）；100 万行 ≈5s+，机械盘/云盘按 3-5 倍计 → 15-25s，**逼近或超过 15s 阈值**；quick_check 同规模仅 170ms。
- **建议**：默认改 `quick_check`，仅在上次异常退出时跑完整 `integrity_check`（可用 shutdown 标记）；FTS 回填移到 listen 之后后台执行；Electron 超时放宽到 60s 并轮询期不判死。

### H5. 前端无代码分割：34 个页面静态打包进单个 bundle
- **位置**：`src/web/hub-tabs.tsx:1-35`（34 个页面全部静态 import，无 React.lazy）；`vite.config.ts`（无 build.rollupOptions/manualChunks）；产物 `dist-web/index-CC48UlV1.js` 414KB + 5.9KB CSS。
- **问题**：Electron 加载即下载/解析全部页面代码（含图表、工作流等重页面），首屏白屏时间与内存占用随页面数线性增长；无 vendor 拆分不利于缓存。
- **量化预估**：414KB JS 解析+执行在低端机 ≈200-500ms 白屏，且每次启动重复；页面继续增加会持续恶化。
- **建议**：hub-tabs 改为 `React.lazy(() => import(...))` + Suspense；manualChunks 拆分 react/vendor/页面组；分析/报表等重页面单独分包。

## 三、中（M）

### M1. 租户过滤 `(clinicId = ? OR clinicId IS NULL)` 削弱复合索引
- **位置**：`src/server/infrastructure/tenant.ts:19`（被 repository.ts、所有 service 复用）
- **问题**：所有 scoped 查询的 WHERE 含 OR 项，SQLite 对 OR 只能做单列索引合并，`(clinicId, deletedAt, createdAt)` 等复合索引无法整体走前缀；`(clinicId = ? OR clinicId IS NULL)` 通常退化为索引扫该列全部值或全表扫。
- **触发条件**：所有带诊所上下文的查询（列表、详情、统计）。
- **量化预估**：100k 行时单查询多扫 ≈10-50ms（与 H1/H2 叠加）；不影响小库（dev 库实测 p95 16ms）。
- **建议**：legacy 数据迁移补齐 clinicId 后改用 `tenantWhereStrict`（tenant.ts:23-27 已存在）；过渡期可接受。

### M2. 全局搜索入口低频但每次击键触发（无防抖）
- **位置**：`src/web/SystemOperationsPage.tsx:14-15,47-49,104`
- **问题**：useEffect 依赖 search，每键触发 `/api/v2/search`（虽有 searchLimiter 限流）。搜索本身用 FTS5（快，实测 7ms），但 6 个资源各一次 IN 查询（read-services.ts:141-250），命中多时串行 6 查。
- **量化预估**：单次搜索 ≈10-30ms（200k 行时），可接受；主要问题是无防抖浪费与限流触发后的体验。
- **建议**：300ms 防抖；搜索结果页对 IN 查询并行化或合并为单条 UNION 查询。

### M3. 同步推送（sync push）逐条写库、无事务、无批上限
- **位置**：`src/server/application/service-modules/sync.ts:73-122`
- **问题**：每个 change 循环内执行 findById + insert/update + record（2-3 条语句），无 db.transaction 包裹（better-sqlite3 每条语句独立提交/fsync）；payload.changes 无数量上限（pull 侧限 1000，push 侧不限）。
- **触发条件**：离线诊所批量同步上传（客户端断网重连后常见，可能成百上千条）。
- **量化预估**：1000 条变更 ≈2000-3000 次独立提交 ≈0.1-0.6s + 无原子性（中途失败部分成功，需重试补偿）；FTS 触发器开启时放大到数十秒（叠加 S1）。
- **建议**：整个 push 包进单个事务；限制单批 ≤500 并分页处理；SyncChange.record 并入同一事务。

### M4. 补货建议生成：全表 SELECT + 逐条 INSERT 无事务
- **位置**：`src/server/application/service-modules/replenishment.ts:18-20`（SELECT * 全部库存）、`:46-82`（每项低于 ROP 单独 INSERT，无事务）
- **触发条件**：点击「生成补货建议」。
- **量化预估**：2000 个库存项、500 条建议 → 500 次独立 fsync ≈0.1-0.5s；包事务后 ≈20ms。库存表量大时 SELECT * 亦拖慢。
- **建议**：包事务；INSERT 改为多行批量；SELECT 只取所需列。

### M5. 收费明细常用聚合无索引
- **位置**：`src/server/application/service-modules/analytics.ts:79-90`（ChargeItem GROUP BY category, name，无 (clinicId, category, name) 索引；实测仅 (chargeId)/(clinicId)/(chargeId,category) 等索引）
- **触发条件**：打开「收费助手-常用项目」。
- **量化预估**：10 万收费 → ChargeItem 30-50 万行，全扫+排序 ≈100-300ms/次。
- **建议**：加 `(clinicId, category, name)` 索引（GROUP BY 可走前缀）或缓存结果。

## 四、低（L）

### L1. 收费/预约创建时逐 relation 字段校验 SELECT
- **位置**：`src/server/infrastructure/repository.ts:194-207`（insert/update 对每个 relation 字段单条 SELECT）
- 量化：索引点查 ≈0.01-0.05ms/字段，可接受；仅在极端批量导入时累计。建议：批量导入路径跳过校验或延迟到事务内。

### L2. 微信批量发送串行 HTTP、单条失败中断整批
- **位置**：`src/server/application/service-modules/wechat.ts:120-126`
- 量化：500 条 × 50ms = 25s 串行；一条失败抛异常中断后续。建议：Promise.allSettled + 并发 ≤10 + 逐条记录失败。

### L3. 预约冲突检测 OR + 时间区间
- **位置**：`src/server/application/service-modules/auth.ts:474-482`
- 量化：10 万预约时 ≈10-50ms/次；建议拆 `doctorId` 与 `chairId` 两条查询或 UNION，复用 (doctorId,startTime) 索引。

### L4. 审计批量刷写：超 50 条时同步事务
- **位置**：`src/server/http/app.ts:65-71,136-140`
- 量化：50 条 INSERT 单事务实测 <1ms，影响可忽略；建议保留（已是批量），仅提示 flushAudit 失败时不应丢日志。

### L5. 文件上传同步写盘 + 收费页患者下拉 200 条全字段
- **位置**：`src/server/http/routes/files.ts:41`（fs.writeFileSync 阻塞事件循环，20MB 磁盘写 ≈20-100ms）；`src/web/ChargesPage.tsx:63-65`（及 VisitsPage 同类）每次打开拉 200 患者 SELECT *。
- 量化：均为几十 ms 级；建议上传改流式/异步队列、下拉改按需搜索。

## 五、10 万患者场景 Top 5 风险

1. **FTS 触发器写放大（S1）**：每笔收费/患者/预约写入 27-36ms 且随库规模二次增长（实测 200k 行 26.5-35.6ms/行 vs 无触发器 0.005ms），收费台是高频操作，50 万收费时单笔 ≈130ms 同步阻塞；批量导入/数据迁移会从 1 分钟级恶化到数小时级。**建议最先处理。**
2. **患者搜索击键即查 + LIKE 全表扫（H2）**：10 万患者时连续打字每秒 2-5 次全表扫，事件循环被占满，前台收银/预约全部卡顿。
3. **仪表盘与经营分析全表聚合（H1）**：65ms@100k → 1s@100 万收费，且 6 个查询并行进入、better-sqlite3 同步串行执行；门诊高峰看板刷新时全局响应劣化。
4. **启动 integrity_check + 迁移回填逼近 15s 健康检查窗口（H4）**：100 万行 + 慢速盘预估 15-25s，Electron 判定启动失败进入重启循环，单机应用将不可用。
5. **幂等清理全表 DELETE（H3）**：日写量 5 千-1 万时每次写多付出 5-10ms 且线性恶化；配合 S1 触发器，单笔收费总开销可达 40-140ms。

## 六、已验证无问题项（排除）

- 备份链路：`backup.ts` 用 SQLite Online Backup API（WAL 下安全、不阻塞写）；`sqlite-files.ts:14-18` 的 `backupSqliteFile` 用 `VACUUM INTO`（安全）；`restore-apply.ts` 流程正确。
- 索引覆盖：Charge（clinicId/paidAt/status/patient/doctor 复合索引齐全）、Treatment（patientId/clinicId 索引存在，`treatmentCount` 点查可走索引）、OperationLog（createdAt 索引存在，每日清理 DELETE 可走索引）、Appointment、UsedRefreshToken、SyncChange 均有完备索引；`charge_ai` 触发器之外的 frequentItems 是唯一明显缺索引聚合。
- FTS 搜索本体：FTS5 MATCH + LIMIT 500 + 6 个 IN 查询，200k 行实测 7ms —— 搜索读路径健康。
- 审计缓冲：50 条/1s 批量落库设计合理，同步刷写成本 <1ms。
- 前端依赖：lucide-react 具名导入可摇树；React Query staleTime 30s/gcTime 5min 配置合理。
