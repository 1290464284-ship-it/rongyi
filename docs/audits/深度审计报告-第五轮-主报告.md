## 一、最重要结论（先说）

1. **资金与库存写路径存在 4 个"看起来成功、实际错账"类缺陷**，其中 ★混合支付全额退款全回会员卡（P0-1）会造成真实现金流损失，★幂等键不含资源 ID（P1-1）可致 B 单静默未收，★发药先扣库存后验批次（P1-2）并发时产生幽灵库存，★退药明细不去重（P1-3）可虚增库存。这四类错误都不会报错——它们静默发生，且难以从账面发现，是本轮最需要优先修复的一组。
2. **启动路径存在确定性性能陷阱**：每次启动 = 无条件 `VACUUM INTO` 全库快照（★migrations.ts:1547-1553，无 pending 迁移检查、无保留策略）+ 启动即执行全量备份（★scheduler.ts:103）+ 全表重建搜索索引（★main.ts:217）。对 1.5GB 级数据库，启动即 2 次全库拷贝 + 百万行级重建，分钟级阻塞，且快照/备份/孤儿 sidecar 均无有效回收（实测 data/backups 100 个文件 138MB ≈ 库大小 40 倍）。
3. **文档与代码漂移已到误导程度**：★README 写默认密码 `admin123`（实际 seed 为 `ry0801`，database.ts:358）；★README 指导 `V2_PORT=3980` 排障，但 vite 代理硬编码 3180（vite.config.ts:53）使该路径必然失败；`docs/refactor-v2-cleanup.md` 引用已删文件与不存在的脚本；MATURITY "92 resources" vs 实际 ~111。建议建立"发布前文档事实核对"清单。
4. **第四轮遗留跟踪项维持**：通用列表 tempPatientPhone 未掩码、dispense 药剂师列表电话直出（产品决策）、分页 NaN→400、CSP 打包实证。本轮又发现 2 处同类手写 SQL 不脱敏（wechat-reminder.ts:249、dispense.ts:204），脱敏策略需在响应边界统一收口。

## 三、15 问逐条答复

### Q1 你觉得你遗漏了什么？（主代理自我反思）

前四轮审计把火力集中在**代码正确性、安全、测试**三个维度，本轮四个子代理暴露了我遗漏的第四个维度——**运行时健康**：

1. **启动路径性能与磁盘增长**：从未有人问过"每次启动系统做了什么"。实测发现启动 = 快照 + 立即备份 + 搜索索引全表重建三连，且快照/staged/sidecar 无回收策略。这是"库大了会出事"的定时炸弹，前三轮完全没覆盖。
2. **数据规模下的索引缺失**：dev 库有遗留索引，掩盖了新库缺 5 类索引的事实。之前的审计只看"现有库跑得动"，没问"干净库/新诊所从零开始跑得动吗"。
3. **文档-代码漂移**：README 密码错误这种"文档事实核对"不在任何门禁里，三轮审计都没人打开 README 对一遍。
4. **资金语义审计**：之前审计校验"退款金额不超过可退额"，但没问"钱退到哪里"。混合支付场景的资金去向是产品语义问题，需要人工推演场景才暴露。
5. 流程层面：前几轮的"有意未修项"没有形成自动复查清单，全靠每轮人工翻报告；建议下一轮开始把跟踪项做成 checklist。

### Q2 你觉得我遗漏了什么？（用户侧盲区）

1. **交付闭环**：代码已推送到远程（上轮完成），但**正式 release 尚未产出**——PR #2 未合并、v2-2.2.0 未打 tag、签名安装包未发布、本地安装包过期（08-06 构建，不含第三轮修复）。这是流程上最实际的一个洞。
2. **灾难恢复演练**：备份功能存在且加密，但**从备份恢复的完整演练**只在 T2R-22 打包验证里做过一次（恢复备份库）；"电脑坏了/硬盘损坏/勒索病毒"场景下，备份文件在同一台机器上、密钥也在同一台机器上——这是单机软件的宿命风险，需要产品层面决策（云备份/异地备份/定期导出）。
3. **数据规模规划**：没有定义"库多大算大"（1GB？10GB？）、何时归档历史数据、审计日志/搜索索引/SyncChange 的保留策略。性能子代理的推算（1.5GB 库年增 550GB 快照）说明规模问题不是"以后再说"。
4. **产品决策待定**：混合支付退款语义（原路退回还是按比例）、多诊所数据可见性（clinic-overview 是否该全诊所可见）、手机号脱敏策略（编辑回填与脱敏冲突）——三个都需要产品拍板，代码只能等。
5. **运维监控**：单机应用无健康检查/磁盘告警；自动备份失败会写 CRITICAL alert（代码里有），但**用户看不到这些告警**——没有通知渠道。

### Q3 你最害怕的是什么？

按发生概率 × 损失排序：

1. **静默数据/资金错账**（P0-1 混合支付退款、P1-1 幂等串号、P1-2 幽灵库存）：这三类错误的共同点是**不报错、不显形**，用户以为成功了，几个月后对账才发现。对诊所软件这是最恶劣的失败模式——比崩溃更可怕。
2. **单机数据全灭**：所有数据、备份、密钥在同一台 Windows 机器上。硬盘损坏、勒索病毒、误删目录 = 诊所全部病历和账目消失。仓库代码已推送（风险已降），但**数据本身没有任何异地副本**。
3. **数据规模增长后的启动瘫痪**：诊所用了 3-5 年，库 1.5GB+，每次启动 2 次全库拷贝 + 百万行重建，用户以为死机，重启更慢。这是"慢性死亡"，最难诊断。
4. **发药/库存被利用**：returnItems 不去重 + 幽灵库存 + 幂等串号组合起来，理论上可以被内部人员刻意触发套库存/套余额。诊所通常不设防内部威胁。

### Q4 技术风险总览

- 资金/库存数据完整性：P0-1、P1-1、P1-2、P1-3（最高优先级）
- 启动性能与磁盘增长：P0-2、P0-3、P2-8
- 干净库索引缺失：P2-6（新部署/新诊所会踩，现有部署被遗留索引掩盖）
- 多诊所/多设备一致性：P1-9、P2-1、P2-3（同步设备数据陈旧）
- 文档误导：P1-7、P1-8（开发与排障成本）
- 单点部署风险：无异地备份、无监控告警（架构性，需产品决策）

### Q5 隐藏 bug
