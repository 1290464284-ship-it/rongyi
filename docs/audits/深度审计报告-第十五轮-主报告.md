## 1. 结论

第 15 轮没有执行代码修复，只做只读审计与结论登记。本轮共确认 39 条问题：后端 P1×6 / P2×11 / P3×3，前端 P1×2 / P2×11 / P3×6。最高风险集中在“库存/账务一致性被静默破坏”和“专用业务路径绕过统一状态机守卫”。

## 2. 后端重点发现（P1）

- 盘点期间仍可出入库，完成时 `setInventoryStock(countedStock)` 会覆盖盘点期间发生的库存变动：`apps/v2/src/server/application/service-modules/stocktake.ts:54,214,266`。`assertNotLocked` 只拦截 `LOCKED`。
- 批次余量与物料总库存可脱节：`inventory-batch.ts:176,305` 的 `consumeFifo/adjust` 只改批次余量，盘点完成只改物料总库存，缺少统一原子口径。
- 退款驳回/取消时会员卡余额用 `Math.max(0, balance - amount)` 静默截断：`refund-flow.ts:181,216`，账目显示已恢复但资金并未真正回收。
- 采购审核 `approve/reject/reopen` 是 check-then-act，UPDATE 不带 `reviewStatus` 条件：`purchase-review.ts:74-115,158-167`。
- 预约时间冲突无数据库级排他约束，多实例可同时通过检查：`appointment.service.ts:136-153`。
- 治疗计划折扣/划价存在过期快照竞态：`treatment-plan-billing.ts:116-145,189-295`。

## 3. 后端重点发现（P2）

- 债务还款未同步 `Charge.paidAt`，佣金按 `paidAt` 统计会永久漏单：`debt.service.ts:39-43`、`commission.ts:151-154`。
- 随访执行 UPDATE 不带 `executionStatus` 条件：`follow-up-execution.ts:60-68`。
- 加工步骤初始化和完成登记无原子守卫：`processing-flow.ts:66-89,133-135`。
- 通知列表/已读只按 `userId`，未按当前 `clinicId` 隔离：`clinical-ops.ts:207,210,216`、`workflow.ts:273-279`。
- 分页 `page=1e308` 可通过校验，offset 溢出为 Infinity 后 500：`pagination.ts:23`、`repository.ts:171`。
- 采购/加工单缺少 supplier/doctor/factory 外键归属校验，`unitPrice*quantity` 无上界：`purchase-order.service.ts:55-63`、`processing-order.service.ts:60-67`。
- 库存事务数量无业务上界，可能整数溢出：`inventory-service.ts:45-50`。
- 快捷划价 `patientId` 缺失会 500 而非 400：`charge-tree.ts:106-108`。
- 密码/禁用变更后 5 秒 refresh 缓存仍可复用旧会话：`auth.service.ts:128-129,321-334`。
- 自动备份告警回调异常会变成 unhandledRejection 并退出进程：`scheduler.ts:68-88,152-153`。
- repository `assertRelations` 在事务外，关联目标可能被并发删除后仍写入：`repository.ts:235,252`。
- 同步设备注册 upsert 无条件覆盖 `userId`，可被并发抢占：`sync.ts:398-411`。

## 8. 你问我答

### 8.1 我遗漏了什么

- 只派出 2 路子代理，Electron/结构与质量没有独立子代理，只做了本地扫描。
- 没有逐条验证全部 P2/P3，部分结论基于静态阅读。
- 没有做真实浏览器截图/无障碍工具扫描。
- 没有对 39 条做修复，本轮定位为只读审计轮。

### 8.2 你（用户）遗漏了什么

- 没有定义“盘点期间是否冻结出入库”的业务规则；当前实现只冻结 LOCKED，完成动作会覆盖期间变动。
- 没有明确“批次余量”与“物料总库存”谁是权威口径。
- 没有为退款冲销余额不足定义“必须抛错”还是“允许部分回收”。
- 没有为金额/数量设置业务上界。
- 没有多实例并发验收标准（现有并发测试多为单进程 Promise 串行）。
- 没有为跨诊所通知/数据隔离建立专项验收用例。
- 没有为上传孤儿文件制定清理策略（4xx only vs 引用计数）。
- 没有 UI 无障碍验收清单（背景 inert、键盘看板等）。

### 8.3 我最害怕什么

最怕“账面上成功、数据里丢失”：盘点覆盖盘点期间的库存变动、批次余量与总库存脱节、退款冲销静默截断、佣金漏单。这些都难以从 UI 察觉，等发现时往往已经不可逆。

### 8.4 技术风险

- 专用业务路径绕过统一 repository/状态机守卫。
- 库存存在“物料总库存、批次余量、盘点快照”三套口径。
- check-then-act 在专用服务中仍然普遍。
- 前端多处“固定页大小当全量”与 `fetchAllPages` 全量拉取并存。
- 上传文件生命周期没有引用计数。

### 8.5 隐藏 bug

见第 2-7 节；最值得先修的是盘点覆盖、批次/库存脱节、退款冲销截断、采购审核条件更新、通知跨诊所、分页溢出。

### 8.6 边界条件

- 超大 page / 超大金额乘积 / 超大数量没有统一上界。
- `patientId` 缺失、`supplierId` 外键归属未校验。
- 分页截断无提示，导出只导已加载行。
- 跨页选择、搜索后选择、资源切换后状态残留。
- 多弹窗叠加与背景可访问性。

### 8.7 性能

- 工作台/时间线/病历表单全量拉取历史数据。
- `fetchAllPages` 在多个页面被当作全量 API。
- 固定 pageSize 当全量且无截断提示。
- 分页/搜索无 `placeholderData` 导致整页 Loading 抖动。

### 8.8 安全

- 通知跨诊所可见是确认的租户隔离缺口。
- 上传孤儿文件与 5xx 清理策略存在数据/存储风险。
- 已确认较好的部分：导航白名单、IPC 信任边界、CSP、证书指纹、审计脱敏、security scan 通过。

### 8.9 重复代码/文件/目录

- src 内无逐字节重复文件。
- `types.ts` / `constants.ts` 同名文件分别有 16 / 10 个，按目录分布但需要定期防漂移。
- `simulated-data.mjs` 疑似旧副本（未被 package.json 引用）。

### 8.10 不易维护的设计

- 状态机守卫散落在各专用服务，模式不统一。
- 库存三套口径并存。
- 前端通用组件存在“造了但没人用”的死亡区。

### 8.11 未来扩展会踩坑

- 多诊所/多实例：通知、预约冲突、同步设备注册都需要数据库级或事务级守卫。

### 8.15 死代码/无用文件
